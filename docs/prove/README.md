<!-- seo: title="Prove: Can exploitability be mechanically demonstrated?" description="Stage 3 of the Agentic Security assurance lifecycle: Can exploitability be mechanically demonstrated?" -->

**Stage 3 of 10.** Can exploitability be mechanically demonstrated?

**Maturity of this stage:** see the table below. Every capability carries its own label.

`triage exploit <id> --prove` executes a bounded, serialized reproducer inside the confined sandbox and lets a deterministic oracle decide whether it worked. The oracle observes mechanical effects (a canary, a callback, exit code and output under a closed set of operators), never what a model says happened.

`EXPLOIT_CONFIRMED` requires the configured number of successful reproductions (three of three by default) **and** an independent re-run in a fresh environment that receives only the reproducer, the finding id, the oracle and the revision.

Run `agentic-security proof doctor` first. It reports which languages this host can run and which isolation boundary it will use. Without a reachable container runtime the proof runs in a lower-assurance local sandbox and is marked `Completeness: DEGRADED`.

**The honest default.** The proof needs a reproducer. You can supply one, and for CWE-78, CWE-22 and CWE-918 `proof generate` can build one. Without a reproducer, nothing runs:

```text
No reproducer for struct:server.js:11:SQL_Injection_(Template_Literal), and none could be generated from the finding: no payload and oracle exist for CWE-89; supported: CWE-78, CWE-22, CWE-918 (others need a database, a deserializer or a na…
```

That is real captured output from the demo app (a SQL injection, which the generator does not support). The finding stays corroborated; it is neither upgraded nor dismissed. A `not-reproduced` result is not a safety proof. The feature has been exercised on macOS only.

**Evidence this stage creates:** A proof record with a state from `CANDIDATE` to `EXPLOIT_CONFIRMED`, the oracle, the reproduction count and the isolation boundary.
