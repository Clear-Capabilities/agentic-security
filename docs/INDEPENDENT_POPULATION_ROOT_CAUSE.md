**96 total.** This leans overwhelmingly toward "shape doesn't occur" over "masked downstream" — the opposite mix from what R16's own speculation entertained ("a fix's effect was masked by something else in the same scan"). Only one of 96 entries turned out to be a genuine downstream-suppression bug, and it wasn't a general suppression mechanism (ignore-pragma, guard-window, reachability) — it was a single detector module (`rate-limit.js`) with a hard-coded field-naming bug that had silently discarded 100% of its own output since it was written.

### 2.1 Two findings outside the category table

- **GHSA-jx74-cqjv-2c67 and 4 siblings (GHSA-4j8x, GHSA-52fh, GHSA-5xvg, GHSA-954p, GHSA-vmv7) are corpus-scoping issues, not engine gaps.** In each, the fix commit's diff shows the real vulnerable code living in a file that was either deleted by the fix (and so never appears in the pre-fix materialized tree) or simply wasn't among the ≤5 files `mine.mjs` selected from a larger squashed commit. The scanner was structurally unable to see the vulnerability regardless of capability. This is a fact about this measurement's sampling, not the engine.
- **GHSA-wg86-r78f-74mp is not a false negative at all.** Re-scanning the cached pre-fix tree produces an active, correctly-located `code-injection-ml` finding (CWE-94) at the exact NodeVM sandbox call sites the fix touches. The scorer counted it as a miss only because the advisory is labelled CWE-95 (Eval Injection, a child of CWE-94 Code Injection) and matching is exact-CWE, not hierarchy-aware. **GHSA-fm2f-4339-4p2f's fix (§3) produces the same shape of result** — the scanner now correctly fires a finding, but under CWE-285 (the detector's own hard-coded BFLA label) rather than the advisory's CWE-862 — meaning the true "genuinely fixed and now scored correctly" count from this session is smaller than the count of "genuinely fixed" fixes, because CWE-hierarchy strictness in the harness independently caps what can register as a TP. This is a property of `matchesCwe`'s exact-match design (`bench/independent/runner.mjs`), deliberately chosen to avoid grading the engine against its own vocabulary — not a defect, but a real, disclosed limit on how much of this session's work the measurement can see.

## 3. What was fixed inline

Three real defects were found and fixed, each gated by a dedicated unit/end-to-end test, the full `npm test` suite (all green), and `bench:cve-replay:check` (215/215, no drift) before landing:

1. **`scanner/src/sast/rate-limit.js` — every finding this detector ever produced was silently discarded** (commit `640da42`). Both `findings.push()` blocks set `title:` but never `vuln:`; `engine.js`'s `_shouldKeep` filter drops any SAST finding with no `vuln` field. The module has been wired into `runFullScan` since it was written and had zero test coverage — exactly how this went unnoticed. Found while root-causing GHSA-r745-8hwv-h473; fixing it does not change that entry's verdict (its labelled CWE is CWE-639 IDOR, a different bug that happens to share a line with the rate-limit finding), but restores an entire CWE-307 detector class project-wide.
2. **`scanner/src/sast/file-upload.js` — new `client-mimetype-trusted` subfamily** (commit `4178312`). Flags a client-supplied `.mimetype` assigned straight to a stored/served `type:` field with no extension-derived lookup nearby (content-type spoofing, still CWE-434). Found via GHSA-944x-pm95-3jpr (Ghost).
3. **`scanner/src/engine.js` + `scanner/src/sast/rbac-consistency.js` — `hasAuth`/role-tier detection missed permission-string RBAC middleware** (commit `27ebf66`). Neither `checkPermission`/`checkAnyPermission`/`hasAnyPermission` was recognized as an auth signal. Found via GHSA-fm2f-4339-4p2f (Flowise BFLA).

**Measured effect on the original 96 false negatives: exactly 1 moved to TP** — GHSA-944x-pm95-3jpr (fix #2). 95 remain FN. Fix #1 (rate-limit.js) could not move any of the 96 by design (no entry in this population is labelled CWE-307). Fix #3 (checkAnyPermission) is independently verified correct via a dedicated end-to-end test, but **did not close GHSA-fm2f-4339-4p2f** — reading the real pre-fix file after the fix landed showed the vulnerable route is registered as `router.put(['/', '/:id'], executionController.updateExecution)`, an array-form path argument that `ROUTE_PATTERNS` doesn't match at all, so the route is invisible to route inventory independent of auth-detection. **This is a disclosed-not-fixed follow-up candidate**, not attempted in this session because extending route-path matching to array-literal arguments is a broader, riskier change than this session's "small, low-risk" bar for inline fixes.

Two further fix candidates surfaced by the batch root-cause pass were evaluated and **rejected** on closer inspection, per the same discipline:

- **GHSA-x3hf-7cj6-3r4m** (missing TypeORM `new DataSource({database: <tainted>})` sink): the batch agent's initial assessment called this a small catalog addition. On inspection, `exprTaint`'s object-literal handling (`engine.js:338`) fires if *any* property of an object-literal argument is tainted, with no per-property targeting mechanism — a plain `argIndex: 0` sink would misattribute a tainted `username` or `type` field on the same config object as "path-controlled file target" too. Real precision risk, not a bounded addition; would need new per-property matching capability.
- **GHSA-gmmw-qg98-6j6p** (BOLA detector not firing on query/body id params): the batch agent that found this explicitly flagged it as needing real corpus false-positive testing before being safe to apply, and this session did not attempt it.

**Kotlin stayed at exactly zero.** The `maven` ecosystem pull that produced the 27 Java entries found no admissible advisory in this batch whose single fix commit had a `.kt` file as its primary changed source — a fact about GHSA's current Kotlin-labelled advisory population at mining time (`mine.mjs`'s admission rule requires exactly one repository fix commit plus a CWE, checked blind to what the engine detects), not a gap in ecosystem coverage. `mine.mjs`'s own `page <= 3`-per-ecosystem ceiling (300 advisories max per ecosystem) is the binding constraint, not the `--limit` flag.

**Four incidental JS/TS entries were also picked up** while mining non-JS ecosystems (2 via `go`, 1 via `rubygems`, 1 unclear — see raw manifest `minedAt: 2026-08-17` entries). This is expected, not a bug: a GHSA advisory's ecosystem tag reflects the package's *distribution channel* (how it's installed — a RubyGems gem, a Go module), not the language of every file its fix touches. `basecamp/trix` is a JavaScript WYSIWYG editor packaged and distributed as a Ruby gem; `aws/aws-cdk` publishes generated bindings to Go/Java/NuGet/PyPI from a TypeScript source repo. `mine.mjs`'s `languageOf(files[0])` picked up the first touched file's extension, which happened to be JS/TS in these cases. None of these four moved to TP.

**Go and Ruby at exactly 0/72 and 0/32 is itself a data point**, not a null result to explain away — worth root-causing in a future pass (this session's scope was mining + root-causing the original 96, not root-causing the newly-mined misses).

## 6. What this does and does not settle

**Settled, with evidence:**
- The original 96 false negatives are now categorized by root cause, not left as an undifferentiated pile — 83 are genuine deeper-engine gaps requiring new source/sink/flow-shape modeling (cross-file, second-order/stored taint, non-web-framework taint sources, code-generation-as-a-sink, library-internal-logic bugs no SAST pattern can express), 6 are legitimate small catalog additions (one shipped this session), 5 are the measurement's own sampling limits (vulnerable file not materialized), and exactly 1 was a real, systemic, silently-broken detector.
- Three real defects were found, fixed, and verified — one of which (`rate-limit.js`) had been completely inert since it was written, affecting every scan this project has ever run, not just this benchmark.
- Java/C#/PHP/Go/Ruby now have real, measured recall figures for the first time. Kotlin remains unmeasurable pending an admissible mined advisory.

**Not settled:**
- **Whether Go's and Ruby's 0% recall reflects a real capability gap or (like the original 96) a mix of corpus-scoping issues and genuine engine gaps.** `n=72` and `n=32` are both below `MIN_RELIABLE_N`'s spirit of "don't over-read a small sample" only in the sense that 0/72 and 0/32 are themselves informative floors, not noise — but *why* they're zero has not been root-caused the way the original 96 were in this session. Candidate follow-up, not started here.
- **How much of R16's original diagnosis question — "shape doesn't occur vs. masked downstream" — generalizes beyond this specific 110→315-entry sample.** This session answered it decisively for the sample it had (83:1 in favor of shape-doesn't-occur), but the sample itself is admittedly biased (`mine.mjs`'s own documented limits: single-repo-fix-commit advisories only, favoring well-maintained projects with good security disclosure practices).
- **GHSA-fm2f-4339-4p2f's array-form route-path gap** (`router.put(['/', '/:id'], ...)`) is disclosed but not fixed. Extending `ROUTE_PATTERNS` to match array-literal path arguments is real, scoped follow-up work.
- **The two rejected fix candidates** (GHSA-x3hf's DataSource sink, GHSA-gmmw's BOLA broadening) remain open — both need either new engine capability (per-property object-literal taint targeting) or corpus false-positive testing before they can safely land.
