# Performance distribution and budgets (E6-08)

Generated by `node scripts/engineering-excellence/perf-budget.mjs`. Every sample is a cold scan of a copy of the corpus in a fresh process, with deep analysis on (the CLI default outside CI).

Hardware: darwin 27.0.0 arm64, 8 cores (Apple M2), 16 GB, node v24.20.0; 1-minute load average at start 2.58. The machine was not otherwise idle.

## How the budgets were chosen

Wall budget = 1.5 x the observed P95, peak RSS budget = 1.5 x the observed maximum, rounded up to a whole second and 50 MB. The rule was fixed before the numbers were seen. The headroom absorbs machine noise; it is a regression tripwire for the machine that measured it, not a service level, and N is small (3 to 7), so a P95 is close to the maximum.

## Warm incremental scans (from the cache measurement, E6-04)

Corpus `scanner/src/sast` (122 files), N=5 per arm, deep analysis off: cold 1685 ms, warm with nothing changed 925 ms (45.1% less), one file changed 982 ms (41.7% less, a speed-up of 1.72x), ten files changed 1081 ms. Warm results were identical to cold results for the same tree: true.

**The planning aspiration of at least 2x for a changed-file scan is NOT met** for the default (non-deep) scan, which is faster by about 1.7x; only the per-file detector stage is cached, and cross-file passes, deep analysis and annotation run every time. No loss of findings was observed.

## Trade-offs and limits

- N is 3 to 7 per class, so P95 is effectively the slowest sample; it describes this machine on this day, not a population.
- Corpora are this repository's own code and fixtures, JavaScript heavy; a Java or monorepo-scale project (the baseline run needed 779 s for apache/camel) is far outside these classes and is covered by the timeout reproduction, not by these budgets.
- Each sample scans a COPY of the corpus in the OS temp folder, with the scan root set and no git history, so history-dependent steps (finding provenance, blame) do not run; an earlier version scanned in place and was several times slower, which is why the first draft of this report is not comparable. Wall time can exceed CPU time when the scan waits on a child process.
- Findings counts are shown to prove every sample did the same work; a changed count would invalidate a comparison.

## Exhaustion is not green

A run that errors, or that finishes with a scan health other than `complete` (a file skipped for size, an analyzer that timed out, a deep-analysis budget stop), makes the class NOT GREEN regardless of its speed; the check exits non-zero.
