# Engineering Excellence: decisions and deviations

Append-only. Each entry says what was decided, why, and what it costs. Entries that deviate from the PRD say so.

## D1. The tracker reuses the loop-engineering primitives instead of duplicating them

`scripts/engineering-excellence/` builds on `scripts/loop-engineering/lib/` for bounded subprocesses (`runBounded`: own process group, wall and idle deadlines, TERM then KILL, orphan sweep, redacted capped logs), atomic JSON writes, the owner-checked file lock, redaction and the schema validator. PRD section 14.1 allows an existing capability only if it is "demonstrably better"; here the existing primitives are reused and the file contract the PRD names (`tasks.json`, `status.json`, `status.schema.json`, `status.mjs`, `runner.mjs`, `logs/<task>/`) is built on top. The loop-engineering controller itself is not used: it drives a different manifest and a different evidence model.

## D2. Dependency edges are hand-written

The PRD states dependencies only per epic. `lib/prd-tasks.mjs` carries an explicit per-task table. Two kinds: `requires` blocks a task until every listed task is verified; `informedBy` is shown but never blocks, so "work from the E1 miss clusters" does not make E2 wait on an external corpus that may legitimately stay unmeasured. The E0 exit gate ("inventory, baseline and status observer work before any epic is marked in progress") is encoded by requiring E0-01, E0-02 and E0-05 transitively from every other epic. A test checks the table is acyclic and that the gate holds.

## D3. Task states are implementation states, not measurement verdicts

`pending`, `in_progress`, `done`, `already_satisfied`, `blocked`, `failed` describe a task. The measurement vocabulary of PRD 3.1 (`passed`, `failed`, `blocked`, `skipped_by_policy`, `not_applicable`, `not_run`, `insufficient_population`, `unmeasured`) is in `lib/model.mjs` as `VERDICT_STATES` and is what baselines, scorecards and gates use. A task can be `done` while a measurement it produced is `unmeasured`. `interrupted` is an audit event, never a stored state.

## D4. A task closes only on commands the runner executed

`task.mjs done` takes no test results from the caller. It reads the commands `runner.mjs` recorded for the current attempt (argv, exit code, log, log SHA-256) and requires a passing run of a test command that names an existing test file, with no later red run of the same command. The latest run decides, so an early pass cannot outvote a later failure.

Cost: evidence logs are machine-local (`logs/` is gitignored, PRD 14.1 allows excluding large files), so a fresh clone cannot revalidate recorded evidence. `status.mjs --resume` and `task.mjs reverify` re-run the recorded test commands and reopen any task whose evidence no longer holds.

## D5. Program bookkeeping does not make the scanner source "dirty"

`measurementIdentity` ignores `scripts/engineering-excellence/status.json`, `events.jsonl`, `data/inventory.verification.json`, `data/baseline.results.json` and `docs/engineering-excellence/**` when deciding `sourceTreeClean`; the number ignored is recorded in `bookkeepingPathsIgnored`. Otherwise every status update would invalidate every measurement taken during the program. Every other uncommitted path, including untracked files, makes the measurement `untrusted_for_release`, and the paths are listed.

## D6. Work happens in a separate git worktree

The 0.172.1 release was being shipped from the main working tree while this program started, and the ship script checks out other refs during its merge phase. The program therefore runs in `../agentic-security-ee` on branch `feature/engineering-excellence`, with `scanner/node_modules` linked from the main tree. The PRD file stays untracked at the worktree root, following this repository's convention for working PRDs; `tasks.json` is the committed, regenerable record of it.

## D7. Maturity labels are computed, and documentation drift is reported rather than silently fixed

`inventory.mjs` computes VERIFIED, PARTIAL, EXISTS-UNVERIFIED, BLOCKED and ABSENT from the source paths, the mapped tests and a recorded test run at the current version. ABSENT items carry the search terms, and the generator re-runs the search.

The first inventory found that five documents state "17 MCP tools" while the server registers 23 (`ALL_TOOLS` in `scanner/src/mcp/tools.js`). The mismatch is shown in the inventory's claims table. The documents are corrected under E8-04 together with the other public documentation, not during E0-01.

## D8. A second worktree needs the generated, gitignored artifacts a fresh `npm install` would create

The first baseline run in the new worktree reported `layer-recall` as failed: Java taint recall 13 -> 0. It was not a regression. `scanner/vendor/java-parser/` is generated by `npm install` (`scanner/scripts/vendor-java-parser.mjs`) and is gitignored, so the worktree lacked it and the Java IR silently fell back to no parser. Running the vendoring script in the worktree restored 13/25, the same value the main tree produces. The failed result is kept in the history of `baseline.results.json` only as superseded; the gate was re-run. Lesson recorded for E6: a missing optional parser degrades one language to zero taint recall without failing the scan, which `scanHealth` should surface (tracked under E6-01).

## D9. The capability ledger excludes `docs/engineering-excellence/`

`scripts/capability-ledger` requires every document under `docs/` to be linked from an index or tracked as a capability. The program's records are generated status and evidence, not capability documentation, so the directory is added to the ledger's `excludedDocPrefixes` with the reason stated there. Public documentation for any command the program adds is written under E8-04 and indexed normally.
