## D-0003: The PRD understates existing infrastructure — verify before building parallel systems

**Date:** 2026-08-23
**Context:** Reading `scanner/src/posture/CLAUDE.md` in full (prerequisite research for E3/E4/E5 work) surfaced substantial existing machinery that overlaps heavily with what the PRD proposes building from scratch:
- `verification-separation.js` already implements producer/verifier separation with write-once provenance stamping and a `consensusOf()` majority vote — this is close to (not identical to) what FR-304/E3's "fresh verification" and E1's evidence/derived-annotation separation (FR-107) ask for.
- `falsification.js` already implements a recall-preserving demotion pass (never deletes, never touches severity) — directly relevant to FR-107 and the PRD's "evidence before severity" principle (§7.3).
- `privacy-framework.js` already implements a **four**-state model (`gap` / `engine-gap` / `manual` / `satisfied`) for NIST Privacy Framework controls specifically, including a documented "vacuous-satisfaction guard" that demotes to `engine-gap` when nothing was scanned — this is materially close to FR-501's six-state control-evidence model (adds `stale` and `accepted_exception`), but currently scoped to one framework's module rather than shared across all compliance mappings (`auditor-walkthrough.js`, which A-07 targets, is a different, older code path).
- `scan-checkpoint.js` already implements resumable scanning with strict invalidation on engine/ruleset/bundle/content-hash/env-var change — this substantially satisfies FR-208, already built.
- `autopilot.js` already enforces "fix applied only if PoC no longer fires AND tests pass," with gates on by default — relevant prior art for FR-304/FR-305, though scoped to the autopilot CLI path, not yet proven to be the *same* gate CLI/MCP/stored-fix all share (that uniformity is still FR-301's open question).
- `fix-history.js` / `fix-verify.js` already run a five-leg verification (rescan + lint + tests + honesty gate + PoC recheck) — closer to FR-305's "required lint/test legs, honest skip reporting" than the PRD's evidence table (A-08) suggests when it says MCP has a stronger gate than CLI/stored-fix; the real gap per A-08 may be narrower (which *entry points* call this shared logic) rather than the logic itself being absent.

**Options:**
1. Proceed to build the PRD's proposed new modules (`pipeline/`, `fix/apply-fix-service.js`, etc.) as greenfield, superseding the existing modules.
2. Treat existing modules as prior art to extend/unify rather than replace, and scope each FR's implementation to "what's the smallest change that makes the *existing* mechanism uniformly applied," per the repository owner's explicit principle: "Prefer new focused modules over expanding `engine.js`" and "fix structural causes, not benchmark-specific symptoms" — building a second, parallel verification/evidence system alongside a working one is itself a structural risk (two systems that can drift, one of which is a false-assurance surface).
**Decision:** Option 2. Every FR's Milestone-1+ implementation work must start with a targeted read of the specific existing module(s) that already address that concern (this decision doubles as a pointer: check `verification-separation.js`, `falsification.js`, `privacy-framework.js`, `scan-checkpoint.js`, `autopilot.js`, `fix-history.js`/`fix-verify.js` before writing new code for E1/E3/E4/E5/FR-208). Where an existing module's contract already matches an FR's acceptance criteria, the work is "wire it up uniformly across every entry point" and "extend its state machine," not "build a parallel one." Where the PRD's evidence-table claim (A-0x) is measurably stale against current HEAD because of this prior work, that will be recorded per-FR in `assurance-hardening-state.json`'s `evidence` field rather than silently accepted.
**Consequence:** Slower per-FR start (each requires reading the relevant existing module before touching it) but avoids the exact failure mode CLAUDE.md's "Verification discipline" section warns about — v0.106.0-v0.107.1 shipped broken because intent was trusted over the actual result. Building net-new "assurance" scaffolding next to working assurance scaffolding, without reconciling them, would be a second instance of that same failure class at architectural scale.
**Reversible:** Yes — this is a research-sequencing decision. If a specific existing module turns out not to fit an FR's contract after inspection, greenfield remains available for that FR alone.

## D-0005: Freezing finalFindings (FR-104) broke deterministic.js's in-place sort — found and fixed via full-gate run, not assumed safe

**Date:** 2026-08-24
**Context:** After implementing FR-101/102/103/104 (producer registry, collector, enrichment-completion, and Object.freeze(finalFindings) at the end of engine.js's runFullScan), the full npm test gate reported 15 failures. Investigated each individually rather than assuming they were all caused by the change (per CLAUDE.md's verification discipline).
**Investigation:**
- 11 of the 15 (`--deterministic makes <format> byte-identical across runs`) were REAL: manually reproduced by scanning a fixture with `--deterministic` and got `TypeError: Cannot assign to read only property '0' of object '[object Array]' at Array.sort ... at makeDeterministic (posture/deterministic.js:87)`. `makeDeterministic` sorted `scan.findings` IN PLACE (`scan[k].sort(sortFn)`), which throws on a frozen array.
- The other 4 (`S7: ... reports "no prior scan" honestly`, across compliance/labs/posture commands) were investigated by running each test FILE standalone: all passed cleanly in isolation. This matches the exact pattern already documented in D-0004 (a prior cycle's mcp-protocol-smoke.test.js flake) — resource contention in the ~4000-test combined run, not a real regression. Not caused by this change: none of these tests touch project-root resolution, temp-directory logic, or anything this cycle's diff modified.
- Searched the codebase (Python-based search, not the shell's `grep`, which was independently found to be unreliable this session — see note below) for every other `.sort(`/`.reverse(`/`.splice(` call site that could plausibly operate on `scan.findings` or `finalFindings`. Found two more: `engine.js:9557` (sorts `finalFindings` — confirmed this runs BEFORE the freeze point, safe) and `report/index.js:1396` (sorts the output of `normalizeFindings(scan)`, which builds a NEW array from scratch — confirmed via re-reading that function during FR-105 that it never returns the same array object as `scan.findings` — safe).
**Decision:** Fixed `makeDeterministic` to build a new sorted array and reassign (`scan[k] = [...scan[k]].sort(sortFn)`) rather than sorting in place. `scan` (the object) is not frozen, only the `findings` array was, so reassignment is legal and produces byte-identical output to the old in-place sort — verified directly (manual reproduction, then the full 12-test format-determinism.test.js suite).
**Consequence:** This is exactly the kind of downstream-consumer breakage the loop's Step 6 adversarial self-review ("can another code path bypass this control... did the change reduce detection recall without evidence") is meant to catch, and it DID get caught — by actually running the full gate and investigating every failure rather than sampling. Reinforces: freezing a shared array is only safe once every legitimate downstream mutator is found and converted to copy-then-mutate. There could in principle be a third, undiscovered site — the full test suite (4000+ tests, including format-determinism, attestation, cross-machine-determinism, pre-push-gate) is the actual safety net here, not the grep sweep, which is why the fix was verified by re-running the full gate again rather than trusting the targeted searches alone.
**Also noted:** this session's shell `grep` (aliased to a custom `ugrep` binary) was found to be unreliable for some patterns during this investigation (a `grep -c export` on a 369-line file with visible `export` statements returned 0). Python-based text search was used as the reliable fallback for the safety-critical parts of this investigation; ordinary greps elsewhere in this session are assumed fine since their results were independently corroborated by passing tests, but this discrepancy is worth remembering if a future grep-based claim looks suspicious.
**Reversible:** Yes — a one-line-shape change to a single function, fully covered by existing tests.

## D-0009: Widespread stray scan state in `test/fixtures/*/.agentic-security/` was corrupting "no prior scan" tests across multiple files — root cause of D-0007, wiped, not a code bug

**Date:** 2026-08-24
**Context:** While verifying FR-601, `test/posture-command.test.js`'s `"no prior scan" honestly` test failed standalone with a real (non-timeout-shaped) assertion mismatch: `parsed.lastScan` was `undefined` instead of `null`. Manual reproduction (after correcting for an unrelated shell-cwd reset caused by an earlier blocked destructive-command hook) showed the CLI's `--status` mode was taking its "has a prior scan" branch inside a supposedly-fresh temp project.
**Investigation:** `test/posture-command.test.js`'s `mkProject()` does `fs.cpSync(FIXTURE, dir, {recursive:true})` where `FIXTURE = test/fixtures/vulnerable-js`. `ls -la test/fixtures/vulnerable-js/.agentic-security` showed real, same-day scan output (`last-scan.json`, `findings.json`, `dpia.md`, `threat-model.json`, etc. — the full artifact set a real scan produces). `cpSync` copies hidden directories by default, so every "fresh" test project silently started with a real prior scan already in it. `find test/fixtures -type d -name .agentic-security` found the SAME pollution in **66 other fixture directories** — this is not specific to `vulnerable-js` or to this session; any test or manual run that scans a fixture directory in place (most plausibly `npm run smoke`, which scans `test/fixtures/vulnerable-js` directly rather than an isolated copy) leaves it there permanently, because `**/.agentic-security/` is gitignored and nothing ever cleans it back up.
**This is also the missed root cause of D-0007** (`test/labs-command.test.js`'s "no prior scan" failures, from earlier this same day) — see the correction appended to that entry. `git stash` cannot remove gitignored untracked files, so D-0007's stash-based falsification correctly proved the bug was unrelated to the session's code diff, but incorrectly concluded it was an undiagnosed pre-existing CODE bug, when the actual cause was accumulated environment state outside git's view entirely.
**Decision:** Wiped every `test/fixtures/**/.agentic-security/` directory (`find test/fixtures -type d -name .agentic-security -prune -exec rm -rf {} +`) — safe, since every file in them is scanner-generated output, gitignored, and fully regenerable. Did NOT change `test:smoke` or any other script to scan into an isolated copy instead of the fixture directory in place — that would be a real, reasonable follow-up (matching how `bench/cve-replay`'s tests already isolate output) but is infrastructure hygiene, not one of the 73 FR-* requirements, and out of scope for this cycle. Documented here instead so it is not re-diagnosed as a code bug again.
**Consequence:** Both the FR-601-cycle `posture-command.test.js` failure and the (now-corrected) D-0007 `labs-command.test.js` failures resolved immediately after the wipe, with zero code changes. Recommend to whoever next touches `test:smoke` or the fixture-scanning tests: either scan a `cpSync`'d copy of `vulnerable-js` instead of the source fixture, or add a wipe step to `pretest`/CI, to stop this from recurring. Flagged, not fixed — same boundary as D-0007's original (correct) scope call.
**Reversible:** Yes — deleting generated, gitignored scan output is trivially regenerable by running any scan again.

**CORRECTION — a real mistake found and fixed immediately after:** the bulk wipe command above (`find test/fixtures -type d -name .agentic-security -prune -exec rm -rf {} +`) deleted two GIT-TRACKED files it should not have touched: `test/fixtures/custom-rules/.agentic-security/rules.yml` and `test/fixtures/sca-suppression/.agentic-security/rules.yml` — deliberately committed fixture configuration for `smoke.test.js`'s "Feat-4: custom rules YAML" and "FP-13: SCA findings honor rules.yml suppressions" tests, not scanner-generated output. **Date:** 2026-08-24

## D-0034: FR-803's "range" and FR-805's "scenario comparison" are the SAME three numbers, computed once — not two independent uncertainty models

**Date:** 2026-08-25
**Context:** FR-803 asks for "ranges, assumptions, source versions, and confidence" on every dollar value; FR-805 (a separate, P2 requirement) asks for "conservative, base, and severe" scenario comparison. Read individually, each could be built as its own mechanism — a `range` computed by, say, perturbing the final EV by a flat percentage, and a SEPARATE `scenarios` object computed by a different named-multiplier scheme.
**Investigation:** Building two mechanisms for what is functionally the same underlying question ("how much does this estimate vary under different assumptions?") would mean maintaining two uncertainty models that could silently drift apart — a range could say $10k–$50k while the named scenarios said conservative=$8k/severe=$60k, with no way for a reader to reconcile them, and no single source of truth for "how uncertain is this number."

There is exactly one place in the code that decides "how much does this vary," and both PRD requirements read from it.
**Consequence:** A future change to the uncertainty model (e.g. adding a 4th scenario, or changing the multipliers) automatically keeps `range` and `scenarios` consistent with each other, because there is only one computation to change. A future contributor should resist the temptation to add a second, differently-scoped "confidence interval" concept to this module — extend `SCENARIO_MULTIPLIERS` and its consumers instead. Multipliers were also deliberately scoped to ONLY the two genuine assumption inputs (probability, impact) — not reachability discount or confidence weight, both of which are measured per-finding facts rather than generic assumptions with real-world spread — documented explicitly in-file so a future reader does not "fix" this by perturbing all four factors uniformly.
**Reversible:** Yes — the multiplier values themselves are tunable constants with no external persistence; changing them changes displayed ranges/scenarios going forward with no migration needed, since nothing about them is stored in the corpus or any baseline.

## D-0042: FR-403 step 1's privacy sink catalog must NOT be merged into catalog.js's shared `CATALOG` export — found during implementation, correcting D-0041's own "zero behavior change" framing

**Date:** 2026-08-25

It is inert: `matchSinkOrSanitizer` never sees these entries, so today's scan behavior is provably unchanged (verified: corpus 215/215 zero drift, self-scan zero drift, full `npm test` clean). A dedicated test suite validates the catalog's OWN shape/coverage (well-formed entries, no duplicate ids, all 9 named categories present, and — the load-bearing assertion — none of its ids appear in the general `CATALOG`), rather than testing live taint detection, since there is genuinely nothing live to test yet.
**Consequence:** D-0041's step 3 (wiring privacy sources/sinks into the real CFG walk) MUST build a privacy-specific matcher that consults `PRIVACY_SINK_CATALOG` (and a future privacy-specific SOURCE set, gated on `privacy-taxonomy.js`'s own classification) as an ISOLATED lattice — never simply merge `PRIVACY_SINK_CATALOG` into the shared `CATALOG` array, no matter how tempting the shorter path looks, because doing so reintroduces exactly the cross-contamination this decision avoided. This is the concrete, load-bearing detail step 3's design must get right; D-0041's own step 3 description ("opt-in second lattice") already implied this, but this entry makes explicit WHY a merge would be wrong, not just that a flag should gate it.
**Reversible:** Yes — `PRIVACY_SINK_CATALOG` is a pure, currently-unconsumed data export; wiring it into a real matcher later (step 3) or discarding it entirely if step 3 takes a different shape are both trivial.

## D-0043: E2's step (a) isolation helper is modeled directly on FR-106's already-shipped `runAnnotatorAsync`, sync-only, not a generic async-capable wrapper

## D-0046: FR-202 requires a real worker-thread boundary; existing timeout mechanisms are cooperative/post-hoc, not preemptive — a concrete 4-phase decomposition, phase 1 built this cycle

**Date:** 2026-08-25
**Context:** FR-202's acceptance criterion is "a deliberately hung analyzer terminates within the configured deadline plus a documented grace period." A dedicated grounding investigation (mirroring D-0039's approach for FR-403) read the two existing timeout-shaped mechanisms in the engine: `engine.js`'s `_perFileTimeoutMs` (measures elapsed time AFTER a file's whole 128-detector pass already completed — a hung detector inside that pass means the check at line ~8528 is simply never reached) and the deep-mode `AGENTIC_SECURITY_DEEP_TIMEOUT_MS`/`deadlineMs` (a cooperative clock-check every 128 worklist iterations inside `dataflow/engine.js` — bounds an already-bounded loop, cannot rescue a hang inside a call that isn't itself instrumented with iteration checks, which is true of essentially all 128 pattern-matching detectors). **Neither mechanism is preemptive.** JavaScript is single-threaded — nothing running in the same event loop as a synchronous infinite loop or catastrophic-backtracking regex can stop it. This is a structural fact, not a code-quality gap.
**Investigation findings:** (1) `src/engine-parallel.js` already exists as dead, unwired scaffolding (`AGENTIC_SECURITY_PARALLEL=1`, zero real callers) — its own header honestly states worker dispatch is deferred because detectors "import 60+ modules with shared state," and its `runParallelFileScans` is a sequential stub. (2) Finding objects returned by detectors are plain JSON-serializable data — safe across a worker's structured-clone boundary. (3) The real complication is shared MUTABLE state several detectors close over as a side channel: `_suppressionLog`, `_GLOBAL_JAVA_TAINTED_METHODS` (module-level, written to alongside a detector's return value, not part of it) and several calls that are not per-file at all (`scanCrossService(aR,fc)`, `scanDbTaintCrossFile(fc)`, the deep-mode IR/taint pass) — these already run in a separate post-per-file-loop pass in the current code, which is the right place for them to keep running even with a worker boundary. (4) Measured cost: ~94ms for the full 128-detector pass on one 42-line file (~0.7ms/detector average) — a worker/thread PER DETECTOR CALL would be dominated by spawn overhead; a worker PER FILE amortizes it far better.
**Decision:** A 4-phase plan, modeled directly on D-0028's FR-201 shape (isolated primitive first, proven with synthetic inputs, real wiring deferred to its own gate-verified step):
1. **(this cycle)** Build `src/pipeline/analyzer-supervisor.js`'s `runWithDeadline(workerData, {timeoutMs, graceMs})` — a real `worker_threads`-based primitive that spawns a worker, races it against `setTimeout(timeoutMs+graceMs)`, and calls `worker.terminate()` (a genuinely preemptive OS-level kill, unlike anything checked-clock-based) if the deadline passes. Proven against a REAL hung synthetic module (an actual busy-wait, not a mock) — the literal FR-202 scenario, at the primitive level. Zero engine.js changes; zero wiring into the real scan loop yet.
2. Design (not yet code) the per-file work-unit contract: what read-only state broadcasts once per worker (gadget sets, tainted-method sets, custom rules) vs. what must convert from a side-channel global (`_suppressionLog`) into an explicit return-value field so a worker's result message can carry it back.
3. Wire real per-file worker dispatch into `engine.js`'s main loop, gated behind an opt-in flag (mirroring `AGENTIC_SECURITY_PARALLEL`'s existing precedent) — keep every cross-file pass (`scanCrossService`, `scanDbTaintCrossFile`, deep-mode) on the main thread exactly where it runs today, running after all per-file workers rejoin. Full accuracy/determinism/self-scan/corpus gate comparison required before this is ever considered for default-on, per the PRD's own §13 performance budget (≤15% median / 25% p95 overhead).
4. Default-path cutover — deferred indefinitely; the PRD's acceptance criterion does not require this to be the DEFAULT execution path, only that the capability genuinely exists and is provably correct when configured, matching this codebase's repeated no-op-until-configured precedent (D-0033, D-0038, FR-802's scenario gate).
**Consequence:** FR-202 will most likely reach a `verified` state at the END of phase 3 (a real, opt-in, gate-verified worker boundary that actually terminates a hung detector during a real scan) without ever requiring phase 4 — phase 4 is explicitly out of scope for the acceptance criterion as written. Whoever picks up phase 2/3 must re-read `_suppressionLog`'s every writer site before assuming it's the only side-channel global; the grounding pass sampled 5 detectors, not all 128.
**Reversible:** Yes — phase 1 is a new, currently-unwired module and its own test-only worker/fixture files; nothing in `engine.js` changes until phase 3.

2. **Confirmed additional broadcast-once candidates** beyond `_GLOBAL_JAVA_TAINTED_METHODS`: `_projectIndex` (built once pre-loop via `_buildProjectIndex`, read-only by `scanLogicVulns`/Java crypto-property lookups during the loop) and `SOURCE_PATTERNS`/`SINK_PATTERNS`/`SANITIZER_PATTERNS` (mutated once pre-loop by `_loadCustomRules` to add operator custom rules, then read-only) — all contain only plain data/Maps/Sets, structured-clone-safe.
3. **Confirmed NO hidden non-per-file detector inside the main loop**, and **NO order dependency between detectors within one file's dispatch** — every in-loop call takes plain immutable strings `(p, cc)`, which structurally forecloses parameter-mutation-based coupling between detectors.
4. **Confirmed `aR`/`fc`/`depFileContents`/`callGraph` have no in-loop cross-file reader** — an earlier file's data never influences a later file's per-file detector results within the same scan; all four are write-during-loop-then-consume-after-loop or entirely post-loop, exactly matching D-0046 phase 3's existing plan to keep cross-file passes on the main thread.
5. **One genuine NEW finding, not anticipated by phase 1:** `src/sast/cpp.js`'s `_entropyMod` is a module-load-time ASYNC singleton (`import('./_secret-entropy.js').then(m => {_entropyMod = m})`) that the current single-process design happens to have resolved before `scanCpp` ever runs (by the time several pre-loop `await`s complete). A worker-per-file design gives each worker a FRESH, independently-racing copy of this same dynamic import with no equivalent warm-up guarantee — an early C/C++ file dispatched to a fresh worker could see `_entropyMod === null` before the import resolves, silently disabling the entropy false-positive filter (the code already fails open by design) and producing extra false-positive hardcoded-secret findings a non-worker run would have suppressed.
**Decision:** The phase-3 work-unit contract (still not built) must: (a) broadcast `SOURCE_PATTERNS`/`SINK_PATTERNS`/`SANITIZER_PATTERNS`, `_projectIndex`, and `_GLOBAL_JAVA_TAINTED_METHODS` once per worker at startup (not per file); (b) convert the 4 `_suppressionLog`-writing detectors' worker-side output to include suppressions as an explicit return-value field, collected and merged into the real `_suppressionLog` on the main thread; (c) fix `src/sast/cpp.js`'s `_entropyMod` race BEFORE any worker wiring lands — either `await import(...)` eagerly and synchronously at worker startup (before the first detector call), or convert to `require()`/a lazy-cached synchronous load — since this is a real, latent correctness bug independent of FR-202 that a worker boundary would only make visible/reachable, not create.
**Consequence:** Phase 3 is now fully scoped with a concrete, verified checklist rather than an estimate. The `_entropyMod` fix is a small, independent, low-risk correction that could land on its own (own tests, own gate run) before or alongside phase 3, per this session's established "fix the pre-existing bug found while researching adjacent work in the same cycle" precedent.
**Reversible:** Yes — this decision only records findings and a checklist; no code changed as a direct result of the audit itself (the `_entropyMod` fix, when it lands, is its own small, reversible, independently-tested change).

## D-0049: FR-202 phase 3 grounding — the per-file loop is checkpoint/resume-coupled; decompose phase 3 into 3a (pure-function extraction, zero worker) and 3b (worker wiring)

**Context:** Cycle 74 began FR-202 phase 3 (real per-file worker wiring, per D-0046's 4-phase plan). Before writing any code, read `engine.js`'s actual per-file loop (inside `runFullScan`, the loop starting at the line containing `let i=0;for(const p of files){...}`) to confirm the shape D-0046/D-0048 assumed still holds.

**Findings:**
1. The pattern-array broadcast assumption is confirmed correct by direct code reading, not just inference: `_loadCustomRules(scanRoot)` runs exactly once, synchronously, before the per-file loop starts (`runFullScan`'s first line: `_resetSuppressions();_buildProjectIndex(fileContents);await _loadCustomRules(scanRoot);`), and it is the ONLY place that `.push()`es onto `SOURCE_PATTERNS`/`SINK_PATTERNS`/`SANITIZER_PATTERNS`. By the time the loop begins, these arrays (plus `_projectIndex`, built on the line just before, and `_GLOBAL_JAVA_TAINTED_METHODS`, built once earlier) are frozen for the rest of the scan. Broadcasting them once per worker at startup is safe and sufficient — confirmed, not assumed.
2. A real complication D-0046/D-0048 did not surface: the per-file loop is **checkpoint/resume-coupled**, not a plain loop. Before each file, `_mk` captures the current `.length` of ~10 shared accumulator arrays (`aR`, `aF`, `aSrc`, `aSink`, `aSan`, `aLogic`, `aSecrets`, `aCiphersRest`, `aCiphersTransit`, `_suppressionLog`); after the file, `_ckptRecord(p, _mk, ms, ta)` slices each array from its mark to its new end and persists that per-file delta so a killed/resumed scan (`_ckptReplay`) can replay exactly the findings that file would have produced, without re-running it. A naive worker-per-file design that just "returns some findings" would silently break resume unless it reproduces this exact delta shape.
3. This complication is actually good news once seen clearly: `_ckptRecord`'s existing delta object (`{routes, findings, sources, sinks, sanitizers, logic, secrets, ciphersRest, ciphersTransit, suppressions, pfr, pfrFindings, ms}`) is **already the exact data contract** a per-file worker needs to return. The checkpoint format was, without anyone designing it for this purpose, already "what one file contributed, as a value" — because resume needed that same isolation. Phase 3 does not need to invent a new return shape; it needs to make the LOOP BODY itself produce that shape as a return value instead of via array-mark-and-slice mutation, and both today's synchronous path and tomorrow's worker path can then consume the same shape.

**Decision:** Split phase 3 into two sub-steps, each independently gate-verified, neither skippable:

- **Phase 3a (this cycle): pure-function extraction, zero worker_threads involvement.** Extract the per-file loop body into a standalone function — `runFileDetectors(p, content, sharedCtx)` or equivalent — that takes the frozen globals as explicit parameters (not closure reads) and RETURNS a delta object shaped exactly like `_ckptRecord`'s existing payload, instead of mutating `aF`/`aSrc`/etc. directly. The main loop calls this function synchronously (today, in-process) and applies the returned delta to the shared arrays itself — behaviorally IDENTICAL to today, proven by full-gate + corpus + self-scan zero drift. This is the safe, reversible half: no new failure mode, no new concurrency, nothing worker-related yet.
- **Phase 3b (next cycle): worker wiring.** Only after 3a is verified byte-identical, make the SAME pure function callable inside `analyzer-worker.js` via `runWithDeadline`, broadcast the frozen globals (`SOURCE_PATTERNS`/`SINK_PATTERNS`/`SANITIZER_PATTERNS`/`_projectIndex`/`_GLOBAL_JAVA_TAINTED_METHODS`) once per worker at startup (via `workerData`, confirmed sufficient since none of them mutate after `_loadCustomRules` returns), gated behind a new opt-in flag, with the checkpoint mark-and-slice mechanism adapted to accept a worker-returned delta the same way `_ckptReplay` already does for a resumed file. Full accuracy/determinism/self-scan/corpus comparison required before this sub-step can be called done, per D-0046's original phase-3 checklist. `analyzer-worker.js` is referenced via a runtime string path to `new Worker()`, not a static import — needs explicit bundling verification (`ncc` will not trace it automatically; already proven working for the FR-202 phase-1 primitive itself in `test/analyzer-supervisor.test.js`, but must be re-checked once the real worker script imports `engine.js`'s exported pure function, a much heavier module graph than the phase-1 synthetic fixtures).

**Why decompose further instead of attempting both in one pass:** the loop touches ~10 shared mutable arrays plus file-skip counters (`_filesSkipped`, `_filesDenseSkipped`) plus per-file timing (`_fileTimings`) plus the checkpoint mark/slice contract — a single combined change (extract AND move to a worker AND adapt checkpointing) has too many simultaneous failure axes to debug if the gate fails, and this session's own established discipline (D-0028, D-0044, D-0046, D-0047) is to never do one large mechanical pass where a smaller, independently-verifiable step is available. Phase 3a alone is fully reversible and adds no new capability — it only changes the DATA FLOW SHAPE inside `runFullScan`, which is exactly the kind of change that should be proven inert before anything concurrent is layered on top.

**Reversible:** Yes, both sub-steps. 3a changes only in-process data flow with an identical synchronous call graph; 3b remains opt-in behind a new flag with phase 4 (default cutover) explicitly out of scope, per D-0046.

## D-0050: FR-202 phase 3b's worker-pool dispatch — reused, long-lived workers with one-time setup, not one-shot-per-file; plus a real cross-test state-leak bug found and fixed along the way

**Context:** Cycle 78 began FR-202 phase 3b's remaining piece: the actual worker-pool dispatch, the one part D-0049 explicitly left un-grounded ("a genuinely new architectural question... has NOT been designed yet").

**The one-shot-per-file model does not scale — a real, load-bearing finding, not a style preference:** `runWithDeadline`/`analyzer-supervisor.js` (FR-202 phase 1) spawns a fresh worker for every call and terminates it after one result — correct and maximally safe for the primitive-level proof, but each fresh worker gets a PRISTINE, unmutated copy of `engine.js`'s module state (`SOURCE_PATTERNS`/`SINK_PATTERNS`/`SANITIZER_PATTERNS` before custom-rule augmentation, an empty `_projectIndex`, an empty `_GLOBAL_JAVA_TAINTED_METHODS`). Reproducing that state requires calling `_buildProjectIndex(fileContents)` / `_buildGlobalJavaTaintedMethodIndex(fileContents)` (both O(total files in the scan)) and `_loadCustomRules(scanRoot)` inside every worker. One-shot-per-file would mean redoing this whole-project work once PER FILE dispatched to a worker — an O(n²) cost across a scan, not a fixed one-time setup cost. This would make opt-in worker dispatch impractically slow for any repo of meaningful size, not just "somewhat slower" — a real correctness-adjacent scaling defect, not a style nit.

**Why a serialization-based broadcast (passing patterns through `workerData`) doesn't work either:** `SOURCE_PATTERNS`/`SINK_PATTERNS`/`SANITIZER_PATTERNS` entries carry function properties (`getLabel`, `inputType`, `fw`, etc.) that are not structured-clone-safe — `postMessage`/`workerData` throws on functions. The correct fix is not to serialize the DATA, but to have each worker independently REPRODUCE it by calling the same setup functions the main thread already calls, using only structured-clone-safe inputs (`fileContents`, `scanRoot` — plain strings).

**Decision:** Build a genuinely separate primitive from `runWithDeadline` — a POOL of long-lived workers (`src/pipeline/cascade-worker-pool.js` + `src/pipeline/cascade-worker.js`), each performing whole-project setup EXACTLY ONCE at creation (via a new exported `_initCascadeWorkerState(fileContents, scanRoot)` in `engine.js`, mirroring `runFullScan`'s own pre-loop sequence), then servicing many per-file `_runFileCascade` task messages for the rest of the scan. A task exceeding its deadline+grace gets its OWN worker terminated (mirroring `analyzer-supervisor.js`'s preemptive `worker.terminate()` precedent) and the pool spawns ONE replacement in the background to stay at full size — a single hung file costs one worker restart, not the whole scan's remaining files. Proven via a synthetic fixture (`test/fixtures/cascade-worker-pool/synthetic-cascade.mjs`) mirroring the same "genuinely separate primitive, tested standalone before any engine.js wiring" precedent as D-0028/D-0046's phase-1 primitives — 8 tests including a REAL hung-task termination-and-pool-recovery proof, and a dedicated test confirming setup runs ONCE per worker across 3 tasks routed to the same single-worker pool, not once per task.

**A real, unrelated bug found and fixed while grounding this (not a hypothetical, a reproduced-and-confirmed leak):** `test/sca-route-reachable.test.js` calls `runFullScan({..., scanRoot: '/tmp/agentic-security-sca-wiring-test'})` — a path that is never actually created on disk. `state-dir.js`'s `resolveProjectRoot()` tries `path.resolve(scanRoot)` first; since that path doesn't exist, `fs.existsSync` is false and resolution FALLS THROUGH to walking up from `process.cwd()` (the real repo, since tests run from `scanner/`), silently redirecting all of `sbom-diff.js`'s state writes into the REAL `scanner/.agentic-security/sbom-history/<real-git-sha>.json` — the exact file self-scan's own dependency-drift comparisons read as "previous." This corrupted the real snapshot with a fake `agentic-security-wiring-test-pkg@4.17.15` component, which then surfaced as a spurious "Dependency removed since previous release" finding attributed (via file-bucketing) to `cascade-worker-pool.js` — a NEW, unrelated file that simply happened to be scanned in the same self-scan run after the leak occurred. Confirmed via direct reproduction: deleting the corrupted snapshot and re-scanning showed the drift persisted, then a controlled, state-disabled scan of the same directory surfaced the REAL, distinct finding underneath (see below) — proving the wiring-test-pkg finding was pure contamination, not something about the new file's content. Fixed by wrapping the test's `runFullScan` call in `AGENTIC_SECURITY_NO_STATE=1` (the same per-test isolation idiom already used in `test/ci.test.js`/`test/fix-metrics.test.js`/`test/no-stray-state.test.js`/`test/streak-cli-wiring.test.js`), and by deleting the one corrupted `sbom-history` snapshot file the leak had already produced.

**A second, genuine finding underneath the contamination, also fixed:** once the leak was cleaned up, self-scan correctly flagged real "Concurrency: fire-and-forget async call — result not awaited" findings on `cascade-worker-pool.js`'s background worker-replacement call (`spawnAndRegister().then(releaseWorker).catch(() => {})`, deliberately not awaited since the timeout handler that triggers it isn't itself awaited by anything). The DESIGN (fire-and-forget background respawn) is correct and necessary — but the bare `.catch(() => {})` silently swallowed a genuine failure mode (e.g., thread/resource exhaustion making every future respawn fail, invisibly shrinking the pool forever). Fixed by capturing the failure into tracked `spawnFailureCount`/`lastSpawnError` state, exposed via `pool.getSpawnFailureCount()`/`pool.getLastSpawnError()`, without changing the fire-and-forget design itself (blocking on it would defeat its purpose). The heuristic still flags the (correct, error-tracked) fire-and-forget pattern and a `return`-propagated promise chain it cannot trace through a function boundary — both reviewed and accepted into the self-scan baseline as the same class of pattern-matcher false positive this session has repeatedly found and accepted elsewhere (`OWNERSHIP-AUTHZ` misfiring on generic vocabulary, cycles 72-73), not rubber-stamped.

**Still explicitly NOT done as of this decision:** wiring the pool into `runFullScan`'s actual per-file loop behind an opt-in flag — the pool primitive is built, tested, and gate-verified in isolation, exactly matching D-0028/D-0046's own "isolated primitive first, real wiring is a separate step" precedent. FR-202 remains correctly `ready`, not `verified`.

**Reversible:** Yes. The pool/worker files are new, currently-unwired modules with zero production callers (confirmed via a clean build producing zero new dist chunks, matching `analyzer-worker.js`'s own precedent of a runtime-string-path `new Worker()` target that ncc does not trace). The `_initCascadeWorkerState` export and `sca-route-reachable.test.js` fix are both small, independently-verified, low-risk changes.

## D-0051: FR-201 completeness correction (scanWeb3Advanced/scanK8sAdmission), and FR-203 grounding — a lightweight coverage ledger over PRD §10.2/§10.3, not a full per-detector AnalyzerResult refactor

**Context:** Cycle 80 began grounding FR-203 ("Produce per-file and per-analyzer coverage ledgers," acceptance: "every in-scope file has exactly one terminal coverage status for every applicable required analyzer") by auditing every one of `_runFileCascade`'s ~130 detector call sites for their applicability rules — the direct prerequisite for building a ledger that says, for each (file, analyzer) pair, what actually happened.

**Correction found and fixed (FR-201, `verified` status unchanged):** the audit found `scanWeb3Advanced` and `scanK8sAdmission` were called directly (`_aF.push(...scanK8sAdmission(p,cc))`), not wrapped in `runDetector` — 2 of the 128 call sites D-0028 step (b) was supposed to have migrated. An exception from either would propagate out of `_runFileCascade` entirely, discarding every OTHER detector's results for that file (everything sequenced after it), a real violation of FR-201's own acceptance criterion. The original migration's grep-based verification (128 sites found = 128 expected) could not catch this because an unwrapped `push(...scanX(...))` and a wrapped `push(...(runDetector(...)||[]))` both contain the substring `scanX(` — counting occurrences of the callee name is not the same as counting occurrences of the WRAPPER. Fixed by wrapping both identically to the other 126 sites; a corrected sweep (grep for `.push(...(?scan*(` specifically NOT preceded by `runDetector`) now confirms zero remaining gaps. Proven via a new fault-injection test (`test/detector-fault-injection-k8s-admission.test.js`) mirroring the existing one's exact `mock.module()` technique. **Lesson for any future call-site audit: verify completeness by the ABSENCE of the old pattern, not just the PRESENCE of the expected count of the new one — a count match can hide exactly this class of gap.**

**FR-203 grounding findings:** PRD §10.2 defines a full `AnalyzerResult` envelope (`analyzerId`, `version`, `scope`, `status` ∈ {`completed`,`partial`,`failed`,`timed_out`,`skipped_by_policy`,`unavailable`}, `startedAt`, `durationMs`, `findings`, `diagnostics`, `coverage`) that each analyzer "must return... rather than mutate shared arrays." FR-201 (already `verified`) does NOT implement this envelope — detectors still return plain finding arrays, and `runDetector` only adds error-capture-and-continue isolation, not the full structured contract. Auditing the cascade's actual applicability gates found the real, tractable shape needed:

- **~119 of ~130 detectors run unconditionally** on every scanned file (no gate at all) — trivially "always applicable."
- **2 are file-extension-gated:** `scanRegexReDoS` (`.java`/`.cs`/`.kt`/`.py`/`.php`/`.phtml`), `scanGraphQL` (`.graphql`/`.gql`).
- **9 are operator-policy-gated** via individual `AGENTIC_SECURITY_NO_*` env vars nested inside one shared `AGENTIC_SECURITY_NO_INTEGRATION` gate (`scanLlmApp`, `scanMobile`, `scanPqc`, `scanWeb3Advanced`, `scanDappFrontend`, `scanCloudIam`, `scanK8sAdmission`, `scanCryptoProtocol`, `scanMlSupplyChain`) — these map DIRECTLY onto PRD §10.2's named `skipped_by_policy` status, an exact, already-existing mechanism the ledger can read rather than invent.
- **1 is content-pattern-gated** (the `.mcp.json` rug-pull block), a structurally different (non-`scan*`) detection shape, out of scope for a `scan*`-detector ledger.

**Decision:** FR-203 does NOT require refactoring all ~130 detectors into full `AnalyzerResult`-returning functions (a much larger, more invasive, higher-regression-risk rewrite of every detector's own contract, which nothing in the acceptance criterion's literal text — "exactly one terminal coverage status" — actually demands). Build a LIGHTWEIGHT coverage ledger computed FROM data that already exists post-FR-201/FR-202: `_detectorErrors` (name + file → `failed`), the file-timeout marker (`_timeout:true` finding → every analyzer for that file becomes `timed_out`, since a preemptive worker kill loses ALL in-flight analyzer state for that file, not just one), the env-var gate table above (→ `skipped_by_policy`, computed once per scan since these are scan-wide flags, not per-file), the 2 extension gates (→ not applicable / excluded from that file's ledger row entirely, not a `skipped` status — PRD wording is "every APPLICABLE required analyzer"), and "ran, didn't throw, wasn't superseded by a file timeout" → `completed`. This mirrors the exact successful pattern of D-0041/D-0046/D-0050: build the smallest correct primitive first (a pure `computeCoverageLedger(...)` function over already-collected signals), test it in isolation, wire it into `scan-health.js`'s currently-`null` `analyzers` field as a separate, later step.

**Reversible:** Yes. The FR-201 fix is a 2-line mechanical change matching 126 already-proven identical sites. FR-203's ledger is scoped as a new, additive, pure-function module with no wiring yet.
