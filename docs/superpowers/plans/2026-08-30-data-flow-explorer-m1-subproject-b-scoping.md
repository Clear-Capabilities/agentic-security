## 1. What already exists to build on

**From Sub-project A (merged, unchanged by this sub-project):** `analyzeFunctionFieldIdentity(fn, entryState) → {exitState, returnFacts, mutatedParams, widenings}` already computes, for ONE function, exactly the shape a per-function "summary" needs — `returnFacts` (per-return-site identity facts), `mutatedParams` (already `Map<paramName, Set<dataElementId>>`, already field-identity-preserving, not boolean) and `widenings`. This is not a coincidence: Sub-project A's own plan said "this anticipates Sub-project B's summary shape without building it." Sub-project B's job is almost entirely about *when and how* to call this function across a call graph, cache its results, and feed a caller's real argument facts into a callee's `entryState` — not about redesigning what the function returns.

**From the taint engine's interprocedural machinery — real, working algorithmic patterns to structurally mirror (never import, never share mutable state, per §18.1 and `scanner/src/lineage/CLAUDE.md`'s isolation rule):**
- `scanner/src/ir/callgraph.js`'s `buildCallGraph(perFileIR, fileContents) → {functions, edges, callersOf, resolve, resolveKnownCallee}` — confirmed **pure** (operates only on already-parsed IR and raw file text for re-export detection, zero taint-specific state) and **directly reusable as-is**, no reimplementation needed. Use `resolveKnownCallee(name, callerFile)` specifically (not `resolve`) — its own docstring recommends it for exactly this use case: "anything resolving a callee purely to build/query a reverse call graph... a wrong guessed edge fabricates a dataflow path that does not exist." It returns a single resolved function, or `null` — never a guessed candidate.
- `scanner/src/dataflow/summaries.js`'s `SummaryCache` class — the CACHING STRATEGY (key = hash of canonicalized entry state, optional caller-qid suffix for call-string sensitivity, optional receiver-type suffix, a per-function distinct-context cap with graceful degradation to an empty-context summary past the cap, a recursion guard returning a "bottom stub" the first time a function is hit while already on the analysis stack, re-resolved by re-invoking analysis up to a small fixed-point cap) is the exact shape to mirror. `_hashState`'s "canonicalize then hash" approach maps directly onto `field-identity.js`'s own `hashState(state)` (built in Sub-project A specifically so this reuse wouldn't require retrofitting later — confirmed working as designed). The CONTENT of a summary (the taint engine's `{returnTainted: bool, mutatedParams: Set<paramName>, ...}`) is explicitly NOT reusable — its own header comment says field sensitivity there is parameter-granularity only, exactly the FR-301 violation Sub-project A spent 6 rounds closing at the intraprocedural level. Sub-project B's summaries use `analyzeFunctionFieldIdentity`'s already-field-identity-preserving shape instead.
- `summaries.js`'s `entryStateFromCall(paramNames, callArgs, callerTaintedVars, isArgTaintedExpr)` — the SHAPE (map call-site arguments to callee-entry facts via an injected resolver closure) is directly reusable; the INTERNALS (boolean `Set<accessPath>` membership) need reimplementing against `resolveExprIdentities`/`residualFlat`/`addIdentity` — the exact primitives Sub-project A already built and hardened across 6 rounds.
- `summaries.js`'s `applyAtCallSite(summary, paramNames, callArgs, callerTaintedVars)` — maps a callee summary's `mutatedParams` back onto the CALLER's own variables at the call site. Confirmed limitation in the taint engine's version: only a bare-identifier call argument gets the mutation propagated back; a `member`-expression argument (`f(obj.field)`) is silently dropped. **Sub-project B's own version should NOT inherit this limitation** — field mutations will plausibly target `obj.field`-shaped arguments often, and `accessPathOf` (already reused throughout Sub-project A) can resolve a `member`-expression argument to a real path just as easily as a bare `ident`. This is a deliberate, scoped improvement over the taint engine's precedent, not scope creep — record it as such when implemented.
- `runTaintEngine`'s driver (`scanner/src/dataflow/engine.js`, `~line 1489-1618`) — two real phases to mirror: **Phase A**, a pre-pass that seeds every function's cache entry under the EMPTY entry state, iterated up to a small fixed cap with real value-equality convergence checking (a documented taint-engine bug once compared only `.size()`, which silently capped convergence early — Sub-project B's own convergence check must use `statesEqual`, not size comparison, from the start); **Phase B**, lazy computation of a function's summary under a REAL (non-empty) entry state only when an actual call site during a caller's real analysis asks for it. A third phase (**Phase C**, speculative receiver-field cross-taint — re-analyzing every method of a class with one method's receiver-field mutations pre-seeded, to catch cross-method field taint without asserting reachability) exists in the taint engine but is explicitly **deferred out of this sub-project's first several increments** (see §3) — FR-302's "receiver fields" requirement is real, but the speculative-then-lazily-confirmed staging this needs is a materially harder problem than the rest of B, and nothing else in B depends on it.

## 2. What's genuinely new — no direct precedent to mirror

- **The interprocedural driver's overall entry point**: something that takes a whole project's parsed IR (multiple files' functions) plus a pre-built call graph, and produces field-identity summaries for every function reachable from wherever the driver is told to start (a specific entry point, or "every function," depending on how this is eventually wired into a real scan — Sub-project B does not need to solve "how does this connect to `runScan`," only "given a call graph and a starting entryState for at least one function, produce summaries" — the CLI/scan wiring is later sub-project territory, matching Sub-project A's own explicit non-goal of "no wiring into `runScan`/the CLI").
- **Deciding what "the call graph" input to Sub-project B's driver actually is** — does it build its own via `buildCallGraph`, or accept a pre-built one from a caller? Recommend: accept one, don't build it internally — keeps the summary/driver logic decoupled from IR-parsing/call-graph-building concerns, matches how Sub-project A's own `analyzeFunctionFieldIdentity` accepts an already-parsed `fn` rather than parsing source itself.

## 3. Recommended decomposition (increments, not "tasks" — each is its own right-sized `writing-plans` plan, following Sub-project A's own established process: plan → SDD execution → task reviews → final whole-branch review → merge)

| # | Increment | Depends on | What it proves/delivers |
|---|---|---|---|
| B1 | **Summary cache core + entry-state-from-call, no real call graph yet** | Sub-project A | A field-identity `SummaryCache` (cache key = `hashState`-based, mirroring `summaries.js`'s key shape), `entryStateFromCall(paramNames, callArgs, callerState) → calleeEntryState` (built on `resolveExprIdentities`/`residualFlat`/`addIdentity`), and `applyAtCallSite(summary, paramNames, callArgs) → {returnFlat, returnByPath, mutationsToApply}` (the ident-AND-member-argument-aware version). Proven against **hand-built two-function call graphs** (no real `buildCallGraph`/`resolveKnownCallee` integration yet) — mirrors how Sub-project A's own Task 1-4 proved the intraprocedural engine against hand-built CFGs before Task 5 brought in the real parser. |
| B2 | **`resolveExprIdentities`'s `call` case consults the cache when a resolution is available** | B1 | The single most important integration point: today, EVERY call in `resolveExprIdentities` is treated as unresolved (union of args, `widened: true`) — this increment gives it a real branch that, given a resolved callee's summary, returns the summary's actual return-facts instead of the generic fallback. Still no real call-graph wiring — the "is this call resolved" question is answered by a caller-supplied lookup function in this increment, deferred to B3 for the real thing. |
| B3 | **Real call-graph integration** | B2 | Wires `scanner/src/ir/callgraph.js`'s `buildCallGraph`/`resolveKnownCallee` in for real, proven against the real JS/TS parser across multiple files (mirrors Sub-project A's Task 5's "real parser" discipline, this time for cross-file real call resolution too). |
| B4 | **The two-phase driver (pre-pass + lazy real-context compute)** | B3 | The actual orchestration loop mirroring `runTaintEngine`'s Phase A/B, producing summaries for a whole small project's worth of functions, not just one call site at a time. |
| B5 | **Recursion handling** | B4 | The bottom-stub + bounded re-analysis mechanism, proven against real mutually-recursive and self-recursive JS/TS functions. |
| B6 | **Context-sensitivity / the per-function cap** | B5 | The distinct-context cap with graceful empty-context fallback past the cap — a lineage-specific env var (not `AGENTIC_SECURITY_KCFA_MAX_CONTEXTS`, a fresh one, keeping the two engines' tuning knobs decoupled per the isolation principle). |
| — | **Receiver-field speculative cross-taint (the taint engine's "Phase C")** | (deferred) | Explicitly NOT part of B1-B6. FR-302's "receiver fields" requirement is partially covered by B1-B6 already (a receiver passed as an argument, or a method's own `this`-qualified param, gets normal parameter-mutation treatment) — the SPECULATIVE cross-method staging is a distinct, harder problem, deferred to a later increment or folded into whichever sub-project needs it most (plausibly C, the path DAG, since speculative-then-confirmed staging interacts with path reconstruction). |

**Recommended first target**: B1. Same reasoning as Sub-project A's own "design spike first" — the summary cache's key shape and the entry-state/apply-at-call-site mechanics are the highest-uncertainty, most load-bearing pieces (get the SHAPE wrong here and every later increment inherits it), and proving them against hand-built call graphs first (cheap, fast iteration, no parser/call-graph-integration noise) de-risks B2-B6 the same way Sub-project A's Tasks 1-4 de-risked its own Task 5.

## 4. Explicitly out of scope for all of Sub-project B (B1-B6)

Receiver-field speculative cross-taint (see table); the path DAG (Sub-project C); source/sink registry integration or transformation-kind recognition (Sub-project D); any `DataFlowGraph v1` graph output (Sub-project E); any wiring into `runScan`/the CLI; any language beyond JS/TS (matching the parent scoping document's own Milestone-1-wide ruling).
