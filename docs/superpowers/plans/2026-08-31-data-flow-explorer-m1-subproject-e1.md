# Data Flow Explorer — M1 Sub-project E, Increment 1: Graph Builder Design Spike

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Resolve, and prove against real parsed code, the design for Sub-project E as a whole — how a real repository's source/sink call sites get matched and seeded into the field-identity engine, how the resulting provenance DAG gets projected into a validated `DataFlowGraph v1` document, and how the sub-project's several inherited obligations (multi-candidate sink resolution, §16.7 Finding 2's enumerator, the coverage ledger shape) get closed. This is a design-and-PoC increment, mirroring every prior sub-project's own first-increment precedent in this PRD (Sub-project A's Decision 1, Sub-project C's C1, Sub-project D's D1) — it produces a committed design-doc ADR and a proof-of-concept regression test proving the mechanism against real code; the mechanical implementation of `graph-builder.js` itself is a follow-up increment (E2 onward), not this one.

**Architecture:** This increment builds NOTHING that ships in the final module set — no `graph-builder.js`, no `source-seeding.js`, no wiring into `runFullScan`. Its entire job is upstream of that: settle, and prove via a throwaway PoC, the exact mechanism so later increments (E2 seeding, E3 the graph builder itself, E4 the coverage ledger, E5 scan-path wiring) have nothing left to design, only to implement against an already-reviewed ADR — exactly D1's role for D2-D5.

**Tech Stack:** Node.js ESM, `node:test` + `node:assert`. No new dependencies.

**Spec:** `docs/superpowers/plans/2026-08-31-data-flow-explorer-m1-subproject-e-scoping.md` in full — §1 (the PRD requirements quoted verbatim, and the three decisions this sub-project inherits already-settled), §2 (the grounded, code-verified gap analysis — read every subsection, not just the summary), §3 (the recommended-not-decided design direction this task evaluates and is free to correct), §4's E1 row (this task's own exact obligations, items a-g), §5 (what this increment must NOT do). Also read directly, not just via the scoping doc's paraphrase: `scanner/src/lineage/driver.js`, `scanner/src/lineage/summaries.js`, `scanner/src/lineage/path-store.js`, `scanner/src/lineage/path-query.js`, `scanner/src/lineage/flow-grade.js`, `scanner/src/lineage/source-registry.js`, `scanner/src/lineage/sink-registry.js`, `scanner/src/lineage/transform-catalog.js`, `scanner/src/lineage/schema.js`, `scanner/src/lineage/validate.js`, `scanner/src/lineage/ids.js`, `scanner/src/lineage/fixtures/build-flagship-fixture.mjs`, `scanner/src/dataflow/catalog.js` (specifically `matchSource`/`matchSinkOrSanitizer`'s own exact signatures and return shapes), `scanner/src/ir/access-paths.js` (`accessPathOf`), `scanner/src/dataflow/index.js` (`runDeepAnalysis`, the structural precedent to mirror per §2.8).

- [ ] **Step 3: Design and prove the seeding mechanism**

Design how a real call site becomes a seeded entry state, per the scoping doc's §3 recommendation (evaluate it, correct it if your own research disagrees):
1. Walk each function's parsed expressions (via whatever the IR/CFG already exposes — you may need `fn.reads`/`fn.cfg` or a fresh walk; determine and document exactly which one, from real code, not assumption).
2. For each expression, call `matchSource(expr, file)`. On a match, take `accessPathOf(expr)` as the field-identity state key.
3. Mint a `dataElementId` for the matched entry via `ids.js`'s `dataElementId(canonicalName, discriminatorParts)` — design the discriminator to satisfy §10.4's "`email` in two unrelated services or schemas must remain two data elements" requirement (at minimum the file path and the access path must be in the discriminator; prove this by constructing two real-looking snippets in different files with the same field name and confirming they mint DIFFERENT `dataElementId`s).
4. Build a seeded entry state (`field-identity.js`'s `addIdentity`, or an equivalent construction — confirm the exact API) per function that has at least one matched source, and decide: does seeding happen INSIDE `driver.js` (an `opts.seedEntryState(fn)` hook, called once per function before `analyzeFunctionFieldIdentity`) or in a wrapper that calls `driver.js`'s lower-level pieces directly? Resolve `driver.js`'s own disclosed cache-overwrite hazard (§2's own quote: "the two computations... are NOT guaranteed to agree... it becomes load-bearing the moment entry states carry real identities") — either by choosing the wrapper approach (bypassing the hazard entirely) or by fixing the hazard as part of adding the hook (a small, additive fix, if that's the chosen shape — this task may modify `driver.js` ONLY for this purpose, per Global Constraints).
5. Run this mechanism against `vulnerable-js` (and ideally `frontend/`) with a `recordHop` recorder attached, and MEASURE the resulting hop count / PathStore size / `sinkCandidates()` count. Compare against the scoping doc's own synthetic-seed numbers (§2.1's second table: 21/21 hops and 9 sink candidates for `vulnerable-js`; 1253/1048 hops and 234 sink candidates for `frontend/`) — your REAL seeding mechanism's numbers will likely differ (probably lower, since it seeds only real matched sources, not every parameter) and that difference is itself a real, reportable finding, not a bug to chase.

- [ ] **Step 4: Design and prove the projection rule, and resolve every remaining E1 obligation**

Using Step 3's real, seeded `PathStore`, design and prove via the PoC:

**(c) Projection.** Per the scoping doc's §3 recommendation ("a graph node is a REGISTRY MATCH, not a provenance node"): enumerate registry-backed sinks (matched via `matchSinkOrSanitizer` at real call sites, reclassified via `reclassifySink`/`reclassifyPrivacySink`); for each, call `reconstructPaths(store, thatSinkNode)`; for each returned `Path` whose terminal corresponds to a seeded source location, materialize ONE `flow` (with the path's `dataElementId`, hop sequence collapsed into graph `edge`s via `ids.js`'s `edgeId`, and `flow.edgeIds` referencing those real `edge:` ids — never `pedge:` ids). Prove on `vulnerable-js`: the resulting graph's node/edge/flow counts are in a sane order of magnitude (compare against the flagship fixture's own 14-node scale, adjusted for `vulnerable-js`'s much smaller size), `validateGraph()` returns `{valid: true, errors: []}`, and — critically, since §2.4 measured that validity alone proves nothing — write your OWN additional assertions the validator cannot make: every `node.subtype` is a real `SOURCE_CATEGORIES`/`SINK_CATEGORIES` value (never a bare `category` string that slipped through unmapped), every `node.dataElementIds` entry is a real dataElement id that exists in `dataElements[]`, no two distinct real call sites collided onto the same node id.

**(a) Seeding location** — resolved by Step 3.

**(b) `dataElementId` minting** — resolved by Step 3, sub-step 3.
