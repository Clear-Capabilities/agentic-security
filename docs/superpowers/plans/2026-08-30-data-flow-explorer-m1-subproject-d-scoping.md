# Data Flow Explorer Milestone 1 — Sub-project D Scoping: Source/Sink Registries + Transformation-Kind Recognition

**Status:** scoping only — no implementation plan yet. Sub-project C (path DAG + bounded reconstruction, increments C1-C6) is DONE and merged to `main` (`b9792a9a`). This document scopes Sub-project D, per the parent Milestone 1 breakdown (`docs/superpowers/plans/2026-08-30-data-flow-explorer-m1-lineage-engine-scoping.md`, §5, row D: *"Reclassifies the existing taint catalog into `DataFlowGraph v1` node kind/subtype categories (FR-101/FR-201's full inventory); adds transformation-kind recognition (mask/hash/tokenize/encrypt/etc., needed for AC-02 per Decision 2). Also delivers 'initial' DB/log/file/queue/HTTP/AI lineage — sink-category recognition only, no field-level mapping (that line is Milestone 2's)."*). Depends only on the Milestone 0 contract (done); sized **Medium** — smaller than A/B/C, because this sub-project's job is RECLASSIFICATION of existing detection capability into a new vocabulary, not building new analysis machinery from scratch (with one real exception: transformation-kind recognition, genuinely new).

## 1. The PRD requirements this sub-project must satisfy

Quoted verbatim from `AGENTIC_SECURITY_DATA_FLOW_EXPLORER_PRD.md`:

- **FR-101 (Complete discovered-source inventory):** *"The graph must inventory all sources found by supported source catalogs and adapters, even when no sink path is resolved."* Source categories: HTTP body/query/route/header/cookie/upload fields; GraphQL arguments/resolver inputs; gRPC request fields; CLI arguments/env values; queue/event messages; database/storage reads; files/object storage reads; user/browser inputs; external API responses; third-party webhook payloads; AI model outputs/tool results/retrieved documents/memory; organization-declared sources. *"Acceptance: **All Sources** shows both connected and disconnected sources, with `modeled`, `partial`, `candidate`, or `unsupported` status."*
- **FR-102 (Field and access-path identity):** *"Sources must be field-sensitive. `user.email` must remain distinguishable from `user.password`, and an object with one sensitive property must not automatically label unrelated properties unless the analyzer explicitly widens because the exact field is unknown."* (Already satisfied by Sub-project A's field-identity engine — this sub-project inherits it, does not re-solve it.)
- **FR-103 (Schema-assisted sources):** *"The system should enrich source fields from OpenAPI, GraphQL, Protobuf, ORM/model declarations, SQL schemas/migrations, JSON Schema, and TypeScript types when available. Schema evidence supplements code analysis; it does not replace observed paths."* (Explicitly "should," not "must" — a stretch item, not a gate; see §4's out-of-scope note.)
- **FR-201 (Complete discovered-sink inventory):** *"All supported sinks must remain discoverable"* — logs/stdout/stderr; HTTP/API responses; browser DOM/client storage; relational/NoSQL databases; files/local storage; object storage/data lakes; caches; queues/topics/streams/event buses; analytics/monitoring/crash-reporting/session-replay; email/SMS/push/collaboration; external APIs/webhooks; AI model providers/local models/agents/tools/vector stores/memory/training/evaluation/telemetry; backups/exports/reports; organization-declared sinks.
- **FR-202 (External destination resolution):** for every outbound call, attempt literal URL/scheme, HTTP method, hostname/port, route/path, SDK/provider, model/service name, env/config chain, cloud resource id, trust zone, recipient org/jurisdiction. Resolution status ∈ `{literal, resolved_from_constant, resolved_from_config, resolved_from_schema, declared_service, runtime_corroborated, dynamic, unknown}`. **Out of scope for D** — this is genuine resolution work (Milestone 2's own line, per the parent scoping doc's exclusions), not category recognition.
- **FR-203 (Unresolved destinations cannot disappear):** *"If the call is known but the destination is dynamic, the graph must create an unresolved external-destination node. The evidence panel must show the expression that prevented resolution."* D's job is to make sure a recognized-but-unresolved sink still produces a node with `coverageStatus`/`externality` honestly set, never silently dropped — the general principle this whole PRD treats as load-bearing (§18.4's own "never translate X into no path," restated here for inventory completeness).
- **FR-204 (Database detail):** full provider/host/db/schema/table/column/operation mapping — **out of scope for D** (Milestone 2's field-level line); D delivers category recognition only ("this call is a database sink") not field mapping.
- **FR-205 (AI destinations):** AI-BOM model/provider/vector-store entries become destination candidates; a sensitive field is shown reaching an AI system only when lineage evidence connects it. D's job: recognize the AI-sink *call site* (model input, prompt/message field, embedding call, vector-store write, tool call, training call, AI telemetry) as a sink category; the AI-BOM linkage itself is Milestone 2's (`DFG-006`/`DFG-... ` per the implementation backlog).

**§10.6 Transformation contract** (the exact shape this sub-project's transform-kind recognition must produce):
> Each transformation must identify: input/output access paths; function/callee and code location; **kind: mask, redact, tokenize, hash, encrypt, decrypt, encode, decode, aggregate, truncate, normalize, custom, or unknown**; reversibility: reversible/irreversible/unknown; algorithm and strength when statically knowable; key-management evidence when applicable; whether the transform applies on all feasible paths or only some; evidence and confidence; control credit granted or denied and the reason. *"Masking, hashing, tokenization, and encryption must never be treated as synonyms."*

**AC-02 (the acceptance criterion this whole sub-project's transform-kind work exists to satisfy):**
> **Given** one path applies a proven `maskCard()` transform to all branches and another logs the raw card number, **then** the masked flow is visibly distinct and may receive handling-control credit, while the raw log creates an issue. Both flows remain visible.

**Decision 2** (the parent Milestone 1 scoping doc, §4, quoted in full — this is the binding scope boundary for D's transform-kind work):
> *"AC-01/AC-02/AC-07's protection-verdict language is satisfied honestly by universal `not_assessed`/`unknown`, except transformation-kind recognition. Milestone 0's `protection.js` treats 'unknown' as a first-class, honest result (Product Principle 2). AC-01 ('each sink shows its own handling, transit, or at-rest verdict') is satisfiable with every edge showing `not_assessed`/`unknown` — that IS a real verdict, just not a resolved one. AC-02 is sharper ('masked flow... may receive handling-control credit') — this needs transformation-kind recognition to exist, but NOT full handling-verdict analysis end-to-end (that's Milestone 2's FR-401-405, separately gated). Recommendation: Sub-project D (transformation-kind recognition) is in scope for Milestone 1; awarding verdict 'credit' from that recognition is explicitly out of scope and stays `not_assessed` until Milestone 2."*

This is the single most load-bearing scope boundary in this document: **D recognizes that a transform of a given KIND happened; D does NOT decide whether that transform earns "protected" credit.** The latter is `protection.js`'s `aggregateVerdicts()` (Milestone 2's job) reading D's output, exactly the same separation-of-concerns C6 just established between `flow-grade.js` (grades evidence quality) and a future consumer (decides display treatment) — this sub-project should follow that same precedent, not invent a new one.

## 2. The gap: what exists today vs. what Sub-project D must produce

A direct code-reading pass (this document's own research, not assumption) found:

- **`scanner/src/dataflow/catalog.js`** (1766 lines) already IS a large, real source/sink/sanitizer registry — 655 entries per `scanner/src/dataflow/CLAUDE.md`'s own count (149 source, 124 sink, 382 sanitizer), spanning nine languages and a dozen-plus frameworks (Express/Koa/Flask/FastAPI/Django/Rails/PHP/Go-net-http/Gin/Echo/Spring/ASP.NET/NestJS). Each entry: `{kind: 'source'|'sink'|'sanitizer', id, language, framework, match: {type: 'call'|'member'|'global'|'annotation', ...}, argIndex, vuln, label, provenance}`. Concrete real examples: `{kind: 'source', id: 'js-req-body', match: {type:'member', object:'req', prop:'body'}, label: 'req.body', provenance: 'http-body'}`; SQL/exec/etc. sinks matched by callee name + receiver-type regex. **This catalog is already field-sensitive-agnostic pattern matching against real parsed IR** — it is the taint engine's detection layer, already proven across the whole benchmark corpus.
- **`scanner/src/dataflow/catalog-expanded.js`** (486 lines, ~450 more sanitizer entries) and **`scanner/src/dataflow/privacy-catalog.js`** (290 lines) extend it further. `privacy-catalog.js` is the single most directly relevant precedent: a **category-tagged** sink catalog (`category: 'log'`, `'response'`, `'storage'`, `'queues'`, `'email'`, `'file'`, `'outbound'`, `'third-party'`) in the EXACT shape `catalog.js` uses, but **deliberately isolated** — not merged into `CATALOG`, not wired into `matchSinkOrSanitizer`/`runTaintEngine` — specifically because doing so would make every already-active general source (`req.body`, etc.) spuriously trigger privacy-leak findings. It is registered in `test/no-dead-modules.test.js`'s ALLOWLIST as *"a deliberate, staged capability with no consumer yet."* **This is close to half of Sub-project D's own sink-category reclassification job, already built and sitting inert, waiting for exactly the kind of consumer this sub-project would add** — but its own `category` vocabulary (`log`, `response`, `storage`, `queues`, `email`, `file`, `outbound`, `third-party`) does NOT exactly match `schema.js`'s `SINK_CATEGORIES` (`log`, `stdout`, `http-response`, `client-storage`, `database`, `file`, `object-storage`, `cache`, `queue`, `analytics`, `monitoring`, `email`, `sms`, `push-notification`, `collaboration`, `external-api`, `webhook`, `ai-*` (9 subcategories), `backup`, `export`, `declared`) — a real reconciliation task, not a drop-in reuse.
- **`scanner/src/lineage/schema.js`** (Milestone 0, already merged) already defines the EXACT target vocabulary this sub-project reclassifies into: `NODE_KINDS` (`source, process, transform, api, store, queue, log, sink, external, boundary, unresolved`), `TRANSFORM_KINDS` (`mask, redact, tokenize, hash, encrypt, decrypt, encode, decode, aggregate, truncate, normalize, custom, unknown` — byte-identical to §10.6's PRD text), `SOURCE_CATEGORIES` (21 values, e.g. `http-body`, `graphql-argument`, `ai-model-output`), `SINK_CATEGORIES` (28 values, e.g. `database`, `ai-vector-store`, `webhook`). **`schema.js`'s own header comment states the boundary explicitly**: *"This is the TAXONOMY only; the pattern-matching registries that recognize one of these categories in real source code (`source-registry.js` / `sink-registry.js`, PRD DFG-003) are Milestone 1, not this module."* This is a direct, pre-existing pointer to exactly what Sub-project D must build — the file names are already named in Milestone 0's own comments.
- **Transformation-kind recognition genuinely does NOT exist anywhere.** A targeted grep across `src/dataflow/`, `src/sast/`, `src/posture/` for `mask`/`hash`/`tokeniz`/`encrypt`/`redact` found no callee-pattern catalog recognizing "this call performs masking/hashing/tokenization/encryption" — only incidental hits (a Rails `where`-clause sanitizer's own comment mentions "hash-form is safe"; secret-detection/PII-logging rules that flag the ABSENCE of protection, not recognize its presence). This is the one genuinely new capability this sub-project must build from scratch, not reclassify from an existing catalog — and it is exactly what AC-02/§10.6/Decision 2 all converge on as the sub-project's real point.
- **No `source-registry.js` or `sink-registry.js` exists** anywhere in `scanner/src/lineage/` today (confirmed: `ls scanner/src/lineage/` — the six Sub-project C modules plus the five Milestone-0 modules, nothing else).

**Conclusion:** Sub-project D is genuinely two different kinds of work under one PRD-scoping row, and they should very likely be sequenced (and possibly even sized) differently: (a) a mechanical-but-real *reclassification* task — reading `catalog.js`'s 273 already-proven source+sink entries (and reconciling `privacy-catalog.js`'s already-half-built sink categories) into `schema.js`'s node-kind/category vocabulary, producing `DataFlowGraph v1`-shaped `source`/`sink` node stubs with honest `coverageStatus` — and (b) a genuinely new detection capability, transformation-kind recognition, which has no existing catalog to lean on and needs its own design pass (what does "recognize a call as a `mask` transform" even mean — a curated callee-name catalog mirroring `catalog.js`'s own convention? Confidence/evidence grading analogous to what C6's `flow-grade.js` already established for flow evidence? These are real open questions, not solved by (a)'s reclassification work).

## 3. Recommended design direction (for the design-spike increment to resolve, not pre-decided here)

Not a final decision — mirrors Sub-project A's own Decision-1 precedent and Sub-project C's own §3 posture (a recommended direction for the FIRST increment to evaluate and correct, not treat as settled):

- **Reuse `catalog.js`'s entries as the INPUT, never the mechanism.** `source-registry.js`/`sink-registry.js` should almost certainly be thin reclassification layers reading `CATALOG`'s existing `{kind, id, label, provenance}` (source) / `{kind, id, label, vuln}` (sink) entries and mapping them onto `SOURCE_CATEGORIES`/`SINK_CATEGORIES` + a `NODE_KINDS` value — NOT reimplementing pattern matching that `catalog.js`/`engine.js` already does correctly and has a full benchmark corpus proving. This mirrors this whole PRD's own "extend-not-fork" principle and Sub-project C's own isolation discipline (a NEW module consuming an EXISTING one's output, never re-deriving it).
- **`privacy-catalog.js` is a strong second input for sink categories specifically**, but its own `category` vocabulary needs reconciling against `SINK_CATEGORIES` first (they overlap but are not identical) — the design-spike increment should resolve this mapping explicitly, entry by entry, not assume a 1:1 correspondence.
- **The `provenance`/`category` string on each existing catalog entry is almost certainly the right join key** to a `SOURCE_CATEGORIES`/`SINK_CATEGORIES` value — but confirm this against EVERY distinct value actually present in `catalog.js`/`privacy-catalog.js` (not just the samples this document quotes), since an unmapped or ambiguously-mapped provenance string is exactly the kind of silent gap this whole PRD's "never let something disappear" principle (FR-203, §18.4) exists to prevent. A source/sink entry with NO confident category mapping should get `coverageStatus: 'unsupported'` or `'candidate'`, never be silently dropped from the inventory.
- **Transformation-kind recognition is its own new catalog, in `catalog.js`'s established shape** (a strong, evidence-based precedent already proven across 655 entries) — a curated `{kind: 'transform', transformKind: 'mask'|'hash'|..., match: {...}, reversibility, ...}` entry list, most plausibly its own file (`transform-catalog.js`, mirroring `privacy-catalog.js`'s own precedent of a family-specific catalog kept separate from the general-purpose `CATALOG`) rather than appended to `CATALOG` itself, since transform recognition has a different consumer (this sub-project's own lineage-node classification) than the general taint engine's vuln-finding pipeline.
- **`coverageStatus` (`modeled`/`partial`/`candidate`/`unsupported`/`manual`) is the mechanism FR-101/FR-201 actually need**, not a nice-to-have — the design-spike increment must decide the exact rule for assigning each of the four values to a recognized-vs-unrecognized-vs-ambiguously-recognized source/sink, since AC-01's own "All Sources shows both connected and disconnected sources, with modeled/partial/candidate/unsupported status" is the literal acceptance test this sub-project's output must satisfy.
- **Do not attempt DB/queue/file FIELD-level mapping** (table/column/schema detail) — the parent scoping doc's own row explicitly reserves this for Milestone 2 ("sink-category recognition only, no field-level mapping"); a `database` sink node needs only `kind: 'sink', subtype: 'database'` plus whatever the taint engine's existing catalog entry already carries (e.g. a matched receiver-type hint), not a real schema-introspection pass.
