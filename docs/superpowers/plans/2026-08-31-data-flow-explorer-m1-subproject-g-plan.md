# Sub-project G implementation plan: privacy comparison report + perf harness extension

Follows the scoping in
`docs/superpowers/plans/2026-08-31-data-flow-explorer-m1-subproject-g-scoping.md`.
Two independent tasks, G1 and G2, both additive, no engine behavior changes.

## G1: privacy comparison report

**New file:** `bench/privacy-recall/compare-lineage.mjs`

- Reuse `measure()` from `bench/privacy-recall/measure.mjs` (old engine:
  shallow + deep counts per fixture, already exercises
  `disableStateWrites`/`purgeScanState`).
- Add a `measureLineage()` function in the new file:
  - For each fixture dir under `bench/privacy-recall/fixtures/*/app.js`,
    parse with `parseJsFile` (`scanner/src/ir/parser-js.js`), build a call
    graph with `buildCallGraph` (`scanner/src/ir/callgraph.js`), then call
    `buildGraphWithCoverage` (`scanner/src/lineage/coverage.js`).
  - Count `graph.dataElements` with non-empty `dataClasses` as the lineage
    engine's "classified" count (mirroring the old engine's finding-count
    shape closely enough for a side-by-side table, while being honest that
    a dataElement count and a finding count are not the same unit — label
    the column accordingly, don't conflate them).
- Emit a combined report to stdout (plain text, `--json` flag mirroring
  `measure.mjs`'s own convention) showing per-fixture: shallow count / deep
  count / lineage-classified count.
- **New doc:** `docs/lineage/PRIVACY_COMPARISON.md` — static write-up (not
  regenerated by the script) containing:
  - The measured table (already known from this session's live run — see
    the scoping doc's G1 section for the exact numbers to transcribe).
  - The root-cause paragraph: old engine classifies by declared variable
    name (`privacy-taint.js` line ~123, `classifyFieldAgainst(d.name,
    compiled)` where `d` comes from `ir.decls`); new engine classifies by
    the source expression's own field name via `classifyDataElementName`
    in `scanner/src/lineage/source-seeding.js` (`classifyDataElementName(canonicalName)`),
    and never inspects downstream variable names.
  - An explicit "not a bug, a disclosed scope boundary" framing, and an
    explicit "changing this is a future-milestone design decision, not
    decided here" non-recommendation — do not implement any classification
    change as part of G1.
- Add a short note (2-3 sentences, following this repo's own "dated
  correction note" convention, not a rewrite) to
  `scanner/src/lineage/CLAUDE.md`'s existing "what is and isn't modelled"
  material, cross-referencing `docs/lineage/PRIVACY_COMPARISON.md`.

**Test:** a new `scanner/test/` or `bench/` regression test is NOT required
here — this is a reporting script over already-tested engines (both
`measure()` and `buildGraphWithCoverage` are independently covered
elsewhere). Instead, verify by RUNNING `compare-lineage.mjs --json` in the
worktree and confirming the numbers match the scoping doc's table exactly
(0/0/0, 0/1/0, 0/1/0, 1/1/0 for shallow/deep/lineage across the 4 fixtures)
before merging — a silent behavior drift in either engine between the
scoping run and the implementation run would itself be worth surfacing, not
just papering over with new "expected" numbers.

## G2: performance harness extension

**Edit:** `bench/data-lineage/perf/runner.mjs`

- Add a new timed step that runs a REAL deep scan (via `runScan` from
  `scanner/src/runScan.js`, same pattern as `bench/privacy-recall/measure.mjs`)
  over a fixed, reasonably-sized target — reuse this repo's own
  `scanner/test/fixtures/vulnerable-js/` fixture tree (already the
  established "smoke" corpus per `scanner/CLAUDE.md`'s test table) since it
  is small, stable, and already a dependency-free target other harnesses
  use — with `AGENTIC_SECURITY_DEEP=1`, both with and without
  `AGENTIC_SECURITY_LINEAGE_DEEP=1`:
  1. Time `runScan(fixtureDir, {network:false})` with deep mode on, lineage
     off. This is the "equivalent deep scan" baseline PRD §21 names.
  2. Time the same call with `AGENTIC_SECURITY_LINEAGE_DEEP=1` also set.
  3. Report the overhead as a percentage: `(withLineageMs - baselineMs) /
     baselineMs * 100`, printed alongside PRD §21's own "no more than 35%
     p50" target text so the number is legible without cross-referencing
     the PRD.
- Wrap both scan calls in `disableStateWrites()`/`purgeScanState()` exactly
  like `measure.mjs` does, and restore any mutated env vars in a `finally`
  block — do not leave global env state mutated after the script exits.
- Keep the existing synthetic-graph generation/validation timing block
  unchanged — this is a pure addition, not a replacement.
- Keep the file's own documented "exits 0 always, no baseline gate yet"
  posture: print the ratio, do NOT add a threshold check or non-zero exit.
  A future milestone (per the file's existing header comment) is the right
  place for a real gate once UI-layer timings exist to gate alongside it.

**Test:** verify by running `node bench/data-lineage/perf/runner.mjs` in the
worktree and confirming it exits 0 and prints a plausible (non-negative,
finite) overhead percentage — no committed baseline, so no regression test
is needed beyond confirming the script runs cleanly.

## Sequencing

G1 and G2 touch disjoint files (`bench/privacy-recall/`, `docs/lineage/`,
one CLAUDE.md note vs. `bench/data-lineage/perf/runner.mjs`) — implement both
in one worktree/task since each is individually small, then one combined
review pass, then merge to local main. Follow this session's established
SDD process: worktree at `.claude/worktrees/m1-subproject-g`, ledger at
`.superpowers/sdd/m1-subproject-g/progress.md`, dispatch one Task
implementer, adversarial review, fix rounds only if findings are real,
`git merge --ff-only` to local main, verify tests on merged main, clean up.
