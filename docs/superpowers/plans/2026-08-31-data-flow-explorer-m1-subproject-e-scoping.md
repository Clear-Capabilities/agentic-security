# Data Flow Explorer Milestone 1 — Sub-project E Scoping: Graph Builder + Coverage/Candidate Ledger

**Status:** scoping only — no implementation plan yet. Sub-projects **A** (field-identity engine core, `field-identity.js`/`engine.js`), **B** (interprocedural summaries + the project-wide driver, `summaries.js`/`driver.js`, B1-B6), **C** (path DAG + bounded reconstruction + FR-306 grading, `path-store.js`/`path-query.js`/`flow-grade.js`, C1-C6) and **D** (source/sink registries + transformation-kind recognition, `source-registry.js`/`sink-registry.js`/`transform-catalog.js`, D1-D5) are ALL DONE and merged to local `main`. This document scopes Sub-project E, per the parent Milestone 1 breakdown (`docs/superpowers/plans/2026-08-30-data-flow-explorer-m1-lineage-engine-scoping.md`, §5, row E: *"`graph-builder.js`: normalizes engine output into the validated `DataFlowGraph v1` envelope; coverage accounting so disconnected sources/sinks stay visible with a reason (AC-11). This is the sub-project that makes the engine's output real graphs for the first time, wired into the existing scan CLI path."*). Depends on A, B and D; sized **Medium**.

Sub-project D's job was reclassification of existing detection into a new vocabulary. Sub-project C's job was a new data structure with a query over it. **Sub-project E's job is neither: it is the first sub-project whose deliverable is an ARTIFACT rather than a capability** — a `DataFlowGraph v1` document, produced from a real repository, that `validate.js` accepts. Everything A-D built is, today, machinery with no caller (measured, §2.0). E is what turns it on.

## 1. The PRD requirements this sub-project must satisfy

Quoted verbatim from `AGENTIC_SECURITY_DATA_FLOW_EXPLORER_PRD.md`:

- **AC-11 (All sources and sinks) — the acceptance criterion this sub-project's second half exists to satisfy:** *"**Given** a detected source or sink has no resolved connecting path, **when** the user opens the corresponding inventory or enables disconnected elements, **then** it is visible with a coverage reason."*
- **§26, Milestone 1 deliverables:** *"complete source/sink inventories and candidate ledger"* — and the exit gate: *"AC-01, AC-02, AC-07, AC-11, and schema completeness pass on the supported-language corpus."* **Schema completeness** is `validate.js` accepting a real graph, and it is E's to deliver; the corpus itself is F's, and running the gate is H's.
- **§27, DFG-011 (P0):** *"Coverage and unresolved-candidate ledger"*, depending on *"DFG-003 through DFG-010"*.
- **§10.2 (Top-level envelope)** — the 17 required top-level keys, already encoded exactly by `schema.js`'s `emptyGraphEnvelope()` (`schemaVersion`, `graphId`, `generatedAt`, `scope`, `scanHealth`, `taxonomy`, `nodes`, `edges`, `dataElements`, `transformations`, `flows`, `controls`, `policies`, `evidence`, `coverage`, `limitations`, `extensions`).
- **§10.3 (Node contract)** — 15 required fields per node, of which `validate.js` structurally enforces six (`id`, `kind`, `label`, `aliases`, `dataElementIds`, `evidenceRefs`, `coverageStatus`, plus `externality.value` when `externality` is present). The other nine (`subtype`, `location`, `system`, `destination`, `lifecycleStages`, `governanceRefs`, `confidence`) are contract obligations `validate.js` is silent about — see §2.4.
- **§10.4 (Data element contract):** *"The identifier must not be based only on the field name. `email` in two unrelated services or schemas must remain two data elements until evidence proves they represent the same logical field."*
- **§10.5 (Edge contract)** — `fieldMappings[]` with `{fromPath, toPath, dataElementIds, mappingType, transformationIds}`, `protocol.destinationResolution`, `boundaryCrossings`, per-edge three-dimensional `protection`, `coverageStatus`.
- **§10.6 (Transformation contract)** — input/output access paths, function/callee and code location, `kind`, `reversibility`, algorithm when statically knowable, key-management evidence, *"whether the transform applies on all feasible paths or only some"*, evidence and confidence, *"control credit granted or denied and the reason"*.
- **§10.7 (Flow contract)** — *"A flow is a source-to-sink projection over graph edges"*, with ordered edge and transformation IDs, alternate-path count, policy verdict, end-to-end protection summary, coverage, and explicit limitations. *"The end-to-end summary … must be derived from the individual edge verdicts, never stored as an unsupported independent claim."*
- **§18.2 (Inputs):** *"The graph builder consumes: Layer-1 IR and call graph; file contents under existing size and admission controls; …"* (thirteen bullets; Milestone 1 can honestly supply only the first two plus the privacy taxonomy — see §4's out-of-scope list).
- **§18.3 (Graph-build phases)** — twelve numbered phases. E owns **1** (inventory expected sources/sinks), **2** (build or reuse IR and call graph — reuse), **4** (run typed field lineage and record compact provenance — drive what A/B/C built), **7** (identify transformations — call D4's recognizer at real call sites), **10** (normalize and deduplicate nodes, edges and flows), **11** (compute coverage and limitations), **12** (*"Validate the graph contract and freeze it before rendering"*). Phases 3, 5, 6, 8, 9 are Milestone 2's.
- **§18.4 (Path-explosion controls)** — six controls plus the constraint this whole PRD treats as load-bearing: *"Never translate 'path budget exhausted' into 'no path.'"*
- **FR-303/305/306** — the compact DAG (C's), multiple paths with a visible count (*"Deduplication may collapse identical internal segments but cannot hide materially different transformations or controls"*), and implicit/widened flows being *"visually distinct and lower-confidence"*.
- **FR-203 (Unresolved destinations cannot disappear):** *"If the call is known but the destination is dynamic, the graph must create an unresolved external-destination node."* D3 shipped the classification half; **E is the per-call-site caller that actually sets it** (§2.5).

### 1.1 Three binding decisions E inherits, already made elsewhere

These are settled. E implements them; E does not re-litigate them.

1. **`category` becomes `subtype`** (`DESIGN_REGISTRIES.md` §9.0, verbatim): *"`category` is the REGISTRY's own field name. On a `DataFlowGraph v1` node it becomes `subtype`. … So D2/D3 emit `category`, and Sub-project E's graph builder writes it to `node.subtype`. Neither side should invent a third name."* A `null` category becomes a `null`/absent `subtype`, and the node's `kind` + `reason` carry the meaning instead.
2. **Protection stays `not_assessed`** (parent scoping doc, Decision 2). Every edge E emits legitimately carries `emptyProtection()` — `{transit, atRest, handling}` all `{verdict: 'not_assessed', evidenceGrade: 'none'}` (measured: that is exactly what `protection.js`'s `emptyProtection()` returns). Recognizing a transformation kind (D4) does **not** license awarding handling credit; that stays Milestone 2's FR-401-405.
3. **§16.7 Finding 2's taxonomy is already decided; its ENUMERATOR is E's** (`DESIGN_REGISTRIES.md`, "Carried forward from Sub-project C", verbatim): *"**Half 1 (the enumerator) is Sub-project E's, not D2's or D3's.** … The consumer that eventually replaces `sinkCandidates()` with real registry-backed sink enumeration is **Sub-project E's graph builder**, and that is where the fix belongs — either by adding the candidate 'truncation-terminal' node shape §16.7 sketches, or by having the enumerator union `diagnostics()`'s degraded targets into its candidate set. **Whoever scopes Sub-project E must pick one up front, because a registry-backed enumerator that simply mirrors `sinkCandidates()`' current kind list reproduces the gap exactly.**"* The node's vocabulary is fixed: *"a `path` node with zero out-edges whose in-edges carry a `context-cap-degraded` annotation is a reportable endpoint, and it carries `kind: 'unresolved'`, `coverageStatus: 'partial'`, `externality: 'unknown'`, with a `reason` naming the context-cap degradation."* §3 below picks one of the two mechanisms as a recommendation for E1 to confirm.

## 2. The gap: what exists today vs. what Sub-project E must produce

Every number below was produced by running real code against the live tree in the session that wrote this document, not quoted from an upstream doc.

### 2.0 The package has no caller at all

`grep -rn "lineage/" src bin --include="*.js"` from `scanner/`, excluding `src/lineage/` itself, returns **one hit, and it is a comment** (`src/ir/parser-js.js:143`, a note that its object-key handling exists so `lineage/engine.js`'s `resolveExprIdentities` can distinguish a computed key). **Nothing under `src/` or `bin/` imports anything from `scanner/src/lineage/`.** Every one of the fifteen modules A-D shipped is reachable only from `test/lineage/*`. `src/lineage/` is also not in `test/no-dead-modules.test.js`'s `SCAN_DIRS` (`['posture','llm-validator','dataflow','lsp','ir','mcp','discovery','sast']`), which is why this has never failed a gate.

This is the literal content of the parent row's *"wired into the existing scan CLI path"* clause, and it is also what `summaries.js`'s own B6 note already disclosed: *"neither `summaries.js` nor `driver.js` is imported by anything under `src/`/`bin/` today (Sub-project E … hasn't landed), so setting this env var currently affects nothing an actual scan run touches."*

### 2.1 The seeding gap, measured: a driver run on real code emits ZERO hops

`driver.js`'s `runFieldIdentityAnalysis(callGraph, opts)` analyzes every function in `callGraph.functions` (qid-sorted) with **`analyzeFunctionFieldIdentity(fn, emptyState(), ctx)`** — literally `emptyState()`, hardcoded at line 72. Its own source comment names the consequence: *"Today every entry state is `emptyState()` (no source registry yet), so no identity can actually differ between the two computations and this is unobservable; it becomes load-bearing the moment entry states carry real identities."* `driver.js`'s own CLAUDE.md row says the same: *"Since the driver analyzes every function from `emptyState()` with no seeding hook (still no source registry — Sub-project E), no hop content can fire from a driver call alone."*

Reading `engine.js` confirms there is no second way in: `analyzeFunctionFieldIdentity(fn, entryState, ctx)` populates its worklist from `entryState` alone, and `dataElementId`s are opaque strings the engine never mints, matches or classifies. **A data-element identity can enter the analysis by exactly one route: a caller putting it in an entry state.** Nothing does.

Measured, on two real JS projects, with a `recordHop` recorder attached to the shipped driver:

| Project | files parsed | functions | **hops from the shipped driver** | PathStore nodes / edges | `sinkCandidates()` |
|---|---|---|---|---|---|
| `scanner/test/fixtures/vulnerable-js` | 1 | 8 | **0** | 0 / 0 | **0** |
| `frontend/` | 33 | 441 | **0** | 0 / 0 | **0** |

The same two projects, re-analyzed with a deliberately seeded entry state (one synthetic identity per parameter — a stand-in for what a real source registry would seed), to show the machinery is live and only the seed is missing:

| Project | functions seeded | hops offered / accepted | join groups | pnodes / pedges | `sinkCandidates()` | paths reconstructed |
|---|---|---|---|---|---|---|
| `vulnerable-js` | 7 | 21 / 21 | 9 | 16 / 9 | 9 (`escape`:9) | 9, all `complete` |
| `frontend/` | 256 | 1253 / **1048** | 369 | **494 / 418** | **234** (`escape`:212, `return`:22) | 284 from the first 200 candidates, all `complete` |

Two things fall out of the second table that E must not be surprised by:

- **Node kinds observed on real code: `path`, `escape`, `return`. Zero `loss`. Zero `origin`.** `path-store.js`'s own §14.2 note already says `origin` is *"hand-fixture-only today, no real-parser fixture reaches it yet"* — and 441 real functions confirm it. So a reconstructed path's `complete: true` does **not** mean it reached an `origin`-kind node; `path-query.js` sets `TERMINAL_ORIGIN` whenever `store.edgesTo(node)` is empty, whatever the node's kind. **On real code, every "complete" path terminates at an ordinary `path` node** — a variable location, not a registered source. Nothing in the store says which of those `path` nodes is a source. That is E's join to make.
- **The DAG is variable-granular, not system-granular.** 494 provenance nodes for a 33-file project, against the flagship fixture's 14 `DataFlowGraph v1` nodes for a whole synthetic payments platform. A 1:1 `pnode → node` projection is not the contract; §3 treats this as the central design question.

### 2.2 What `path-store.js` / `path-query.js` actually hand a consumer

Read from source, not paraphrased:

- **`PathStore`** is a pure consumer of the 14-field hop record (`HOP_FIELDS = ['kind','subKind','scope','dataElementId','fromPath','toPath','syntacticPath','nodeId','line','widenReason','lossReason','context','peerScope','peerContext']`). Its read API is `nodes()`, `edges()`, `getNode(id)`, `getEdge(id)`, `nodeIdFor(desc)`, `edgesFrom(id)`, `edgesTo(id)`, `hasEdge(from,to)`, `stats()`, `diagnostics()`, plus `addHop`/`addHops`/`markTruncated`. Every read is an O(1)/O(degree) index lookup; there is deliberately no traversal.
- **A provenance node** is `{id: 'pnode:<kind>:<hash>', kind, scope, context, path, siteNodeId, dataElementId, truncated}` where `kind ∈ {path, return, escape, loss, origin}` and `context` is `hashState(entryState)`. **A provenance edge** is `{id: 'pedge:<hash>', fromNodeId, toNodeId, dataElementId, scope, context, siteNodeId, inKind, inSubKind, outKind, outSubKind, widenReasons[], lossReasons[], line, crossScope, originated, ambiguousCorrelation, annotations[], truncated}`.
- **`diagnostics()`** returns four buckets: `malformed`, `unclassified`, `truncations` (from `markTruncated`), and `orphanedPeerSources`. Measured on the seeded `frontend/` run: all four empty.
- **`reconstructPaths(store, startNodeId, opts)`** returns a `ReconstructionResult`: `{startNodeId, startNodeKind, unknownStartNode, paths[], truncated, truncationReasons[], noPathReason, enumeratedPathCount, returnedPathCount, droppedPathCount, completePathCount, cyclesClipped, terminals[], analysisTruncated, budget}`. Each `Path` is `{id: 'ppath:<hash>', nodeIds[], edgeIds[], hops[], hopCount, dataElementId, sourceNodeId, sinkNodeId, terminal:{nodeId,reason,kind}, complete, crossScopeCount, widenedHopCount, lossHopCount, ambiguousHopCount, analysisTruncated, shape}`. The `edgeIds` are `pedge:` ids and the `nodeIds` are `pnode:` ids — **neither namespace is a `DataFlowGraph v1` id**, deliberately (`ids.js`: *"a provenance node is NOT a `DataFlowGraph v1` node, and `validate.js`'s id-prefix regexes must never be able to confuse the two namespaces"*).
- **`sinkCandidates(store)`** returns every `return`/`escape`/`loss`-kind node, with *"no notion of whether any of them is a security-relevant sink — that judgment belongs to Sub-project D's eventual registry."* It is the registry stand-in E replaces.
- **`isIncompleteAnswer(result)`** is AC-10's five-term banner predicate, exported so no caller re-derives it.
- **`flow-grade.js`** exposes `gradeHop(hopOrEdge)` → `{grade, rank, factors[], widenReasons[], lossReasons[], implicitReasons[], annotationOnly[], ambiguousCorrelation, degraded, truncated, crossScope, incomplete}` and `gradePath(path)` → the same plus `hops[]` (full per-hop grades), `worstHopIndex`, six per-kind counts, and `complete`/`incomplete`. `FLOW_EVIDENCE_GRADES = ['explicit','widened','implicit','severed','ambiguous','unassessed']`. `flow-grade.js` has **zero imports** and never touches the store.

### 2.3 What the registries actually return, and one asymmetry E must handle

- `reclassifySource(entry)` → `{kind: 'source', category, coverageStatus, externality, reason}`; `kind` is always `'source'`.
- `reclassifySink(entry, opts)` → the same shape, but `kind` is **category-derived** (`CATEGORY_NODE_KIND`: `log`→`log`, `database`/`file`/`object-storage`/`cache`/`client-storage`/`backup`/`export`→`store`, `queue`→`queue`, `external-api`/`webhook`/`email`/`sms`/…/`ai-*`→`external`, `http-response`/`declared`→`sink`, `ai-local-model`→`process`), with `category === null` → `kind: 'process'`, `coverageStatus: 'unsupported'`, `externality: 'internal'`.
- `reclassifyPrivacySink(entry)` → the same shape for the 18 `PRIVACY_SINK_CATALOG` entries.
- `recognizeTransformation(calleeDescriptor)` → `{kind, reversibility, algorithm, confidence, evidence}` or **`null`**, where `calleeDescriptor` is `{type:'call', callee}` / `{type:'member-call', object, method}` / a dotted string. `NEVER_EMITTED_KINDS = ['custom','unknown']` — the recognizer's honest answer for an unrecognized callee is `null`, and *"choosing between `custom` and `unknown` belongs to whoever must still materialize a Transformation entity"*, i.e. E.

**The registries reclassify ENTRIES; they never see a call site.** Running the match is E's. Measured on `scanner/test/fixtures/vulnerable-js/app.js`, calling `dataflow/catalog.js`'s own matchers against the same `parser-js.js` IR the lineage engine walks:

- `matchSource(expr, file)` — **9 call-site matches, 3 distinct entries** (`js-req-body`, `js-req-query`, `js-req-params`), and `accessPathOf(expr)` on each yields exactly `req.body` / `req.query` / `req.params`: **directly usable as a `field-identity.js` state key**. This is the existence proof that the seeding mechanism §3 recommends is viable.
- `matchSinkOrSanitizer(calleeExpr, file, receiverType)` — **12 call-site matches, 6 distinct entries**, which `reclassifySink` maps to: `js-sql-query`→`store`/`database`/modeled, `js-express-res-send`→`sink`/`http-response`/modeled, `js-koa-send`→`store`/`file`/modeled, `js-fs-readFile`→`store`/`file`/modeled, and `js-exec`/`js-eval`→`process`/`null`/**unsupported** (code-execution CWEs with no data DESTINATION — exactly the `unsupported`-with-reason node D3 insists must be preserved, never dropped).

**The asymmetry, and it is a real one:** `matchSource` returns **one entry or `null`**; `matchSinkOrSanitizer` returns an **ARRAY of candidates**. Measured: `res.send(x)` returns **two** sink candidates from two different `SINK_CATEGORIES` — `js-express-res-send` (CWE-79 → `http-response`) and `js-koa-send` (CWE-22 → `file`). A graph builder that naively takes `[0]` picks by catalog authoring order. This is the same class of problem D3's `thirdPartySdk` note already flagged as *"only decidable AT MATCH TIME, from the receiver that actually matched: information a registry reclassifying ENTRIES never sees. … A match-time consumer that knows the matched receiver can promote `partial` → `modeled`."* **E is that match-time consumer**, and multi-candidate resolution is a decision E1 must make explicitly rather than inherit from array order.

### 2.4 What `validateGraph()` structurally requires — and what it does NOT

Measured by running `validate.js` against constructed inputs:

- **`emptyGraphEnvelope({graphId})` validates `{valid: true, errors: []}`.** An empty graph is a legal graph. **Validity is therefore not evidence of coverage** — this is precisely why AC-11 needs its own accounting and cannot be satisfied by "schema completeness passes".
- A node built as `{id, kind, subtype, label}` produces four errors: `aliases`, `dataElementIds`, `evidenceRefs` must each be arrays, and `coverageStatus` must be a `COVERAGE_STATUS_VALUES` member. So the minimum viable node is `{id: 'node:…', kind ∈ NODE_KINDS, label: non-empty, aliases: [], dataElementIds: [], evidenceRefs: [], coverageStatus ∈ {modeled,partial,candidate,unsupported,manual}}`, plus `externality.value ∈ EXTERNALITY_VALUES` if `externality` is present at all.
- An edge with `{id, from, to, relationship:'data_flow', fieldMappings:[]}` produces exactly one error: **`edge.protection is required`**, with all three of `PROTECTION_DIMENSIONS` (`transit`, `atRest`, `handling`) individually valid. `emptyProtection()` satisfies it.
- Referential integrity IS enforced for: `edge.from`/`edge.to` ∈ node ids; `edge.fieldMappings[].dataElementIds` ⊆ dataElement ids; `flow.source`/`flow.sink` ∈ node ids; `flow.dataElementIds` ⊆ dataElement ids; **`flow.edgeIds` ⊆ EDGE ids** (so a `pedge:` id can never be put in `flow.edgeIds`). Plus duplicate-id detection across all four of `nodes`/`edges`/`dataElements`/`flows`.
- **It is NOT enforced for**: `node.subtype` against `SOURCE_CATEGORIES`/`SINK_CATEGORIES` (no check exists at all — a registry `category` written to `subtype` is unvalidated); `node.dataElementIds` against the dataElement ids (only checked to be an array); `node.location`/`system`/`destination`/`lifecycleStages`/`governanceRefs`/`confidence` (§10.3 obligations `validate.js` is silent about); `transformation` fields beyond `id`/`kind`/`reversibility`; and the entire shape of `coverage`, `scanHealth`, `taxonomy`, `limitations` contents (arrays/objects only).

**The consequence for E, stated plainly: naively wiring A-D together and getting `valid: true` proves almost nothing.** The two failure modes E must design against are (a) a graph that validates and is empty, and (b) a graph that validates and is silently wrong in the seven places `validate.js` does not look. D's own `D1/1e` non-empty-`reason` and `D1/3c` biconditional tests are the precedent: the assertions that matter are the ones the validator cannot make.

One further validator-adjacent obligation: `ids.js`' content-hash discriminators must be complete. The package's own CLAUDE.md records the lesson: *"Entity-id discriminators … must include every field that can vary between two otherwise-similar entities (e.g. an edge's `dataElementIds`) — two edges over the same node pair carrying different payloads collided on id once before this was tightened."* With `_checkDuplicateIds` now shipping, an under-specified discriminator is no longer a silent merge — it is a **validation failure**, which is better, but it means E's discriminator choices are load-bearing from the first commit.

### 2.5 FR-203's caller does not exist yet, and D3 named E as it

`reclassifySink`'s `opts.destinationUnresolved` is documented as: *"set by a FUTURE per-call-site caller (Sub-project E's graph builder — no catalog entry carries per-call-site destination information, §7.5, so this can never be true from CATALOG data alone today) when the RECOGNIZED sink's actual destination could not be statically resolved."* With `opts.blockingExpression` it returns `kind: 'unresolved'`, category retained, `externality: 'unknown'`, `coverageStatus` **unchanged**, and a `reason` naming the blocking expression. **Nothing calls it with that option today.** E is the caller, and E must keep this case structurally distinct from §16.7's degraded-analysis `unresolved` (which carries `coverageStatus: 'partial'` unconditionally, for an unrelated reason) — D3's own header warns against conflating them at length.

### 2.6 §16.7 Finding 2, restated as E's concrete obligation

Measured by C6 and recorded in `DESIGN_PATH_PROVENANCE.md` §16.9's last row: on the context-cap-degraded fixture, sink-rooted reconstruction yields **6 paths, 25 hops, zero `severed` grades and zero degraded path grades** — the degradation marker is intact in the store, graded correctly the moment anything looks at it (`C6/6`), *"what is missing is that nothing asks."* The degraded `call-arg-bind` edge's target is an ordinary `path` node with zero out-edges, so it is neither a `sinkCandidates()` result nor on any path to one. §18.4's constraint re-opens at the query boundary. **E's registry-backed enumerator closes it or reproduces it; there is no third option**, and the taxonomy for the node it must produce is already fixed (§1.1 item 3).

### 2.7 Two smaller, concrete facts worth knowing before planning

- **`emptyGraphEnvelope()` defaults `generatedAt` to `new Date().toISOString()`.** `scanner/CLAUDE.md`'s determinism convention is that `--deterministic` must produce byte-identical output run-to-run. `graphId` is already deterministic (`dfg:<repo>:<commit>:<configHash>`); `generatedAt` is not. E must decide what a graph emitted from a `--deterministic` scan carries.
- **`scope.source` defaults to `'scan'`**, and the flagship fixture explicitly sets `'fixture'`. That default is the generic signal Appendix D.1 requires (no special-casing by filename) and is what makes Sub-project G's fixture-vs-real comparison possible — E should not touch it, and should not set it.

### 2.8 The existing integration point, read from source

`runScan`'s deep path lives in `scanner/src/engine.js` around lines 9129-9200:

```

const _buildIR = async () => (_hasJava ? await buildProjectIRAsync(fc) : buildProjectIR(fc));
…
if (_deepEnabled) {
  const { perFile, callGraph } = _sharedIR || (_sharedIR = await _buildIR());
```

Two structural facts this establishes:

1. **`{perFile, callGraph}` already exists at exactly the point E needs it**, memoized in `_sharedIR`, and is exactly the shape `driver.js` documents as its input (*"`callGraph` must be a real object from `scanner/src/ir/callgraph.js#buildCallGraph` (`{functions, resolveKnownCallee, …}`)"*). E needs no new IR pass.
2. **`dataflow/index.js`'s `runDeepAnalysis(perFileIR, callGraph, opts)` is the right structural precedent to MIRROR — and only to mirror.** It is a package-level entry point that owns budgets, env gating, optional extra passes and a best-effort try/catch, and returns a result the caller appends. It also contains the exact precedent for how an isolated, opt-in parallel analyzer is added without touching the primary engine: the `AGENTIC_SECURITY_PRIVACY_DEEP` block, whose own comment reads *"Mirrors the IFDS wiring above exactly — an additional pass whose findings are merged in, never replacing the primary engine's output, and whose failure must never fail the scan."* E should copy that SHAPE. E must not import `runTaintEngine`, `runDeepAnalysis`, `SummaryCache` or anything else carrying taint state (§18.1: *"may not share mutable taint state with the general engine in P0"*); the only `dataflow/` imports the lineage package takes today are pure data and pure functions (`CATALOG`, `PRIVACY_SINK_CATALOG`, `access-paths.js`'s helpers), and adding `matchSource`/`matchSinkOrSanitizer` to that list is the one reuse question E1 must confirm explicitly rather than assume (`DESIGN_REGISTRIES.md` §1 already blesses the direction: *"They never re-derive what a call site matches — `matchSource` / `matchSinkOrSanitizer` / `matchPrivacySink` already own that, and duplicating it would fork a matcher the corpus proves against one that nothing proves"*).

### 2.9 Conclusion

Sub-project E is three distinguishable pieces of work, and they should be sequenced rather than attempted at once:

1. **Seeding** — make an analysis run produce hops on real code at all (match sources at real call sites, mint `dataElementId`s, build entry states, drive, record). Without this, everything downstream operates on an empty store; measured at exactly **0 hops** today.
2. **Projection** — turn a variable-granular provenance DAG (494 nodes / 418 edges on one 33-file project) into a system-granular `DataFlowGraph v1` (14 nodes for a whole synthetic platform). This is not normalization-in-the-small; it is a genuine modelling decision with no precedent in the tree except a hand-written fixture generator.
3. **Coverage accounting** — AC-11's ledger, plus the two "must never disappear" obligations E specifically inherits (FR-203's caller, §16.7's enumerator). This half is what an empty-but-valid graph would silently skip.

## 3. Recommended design direction (for the design-spike increment to resolve, not pre-decided here)

Not a final decision — mirrors Sub-projects A/B/C/D's own precedent of a recommended direction the FIRST increment evaluates and is free to correct.

- **Mirror `runDeepAnalysis`'s shape; import nothing from it.** A new `scanner/src/lineage/index.js` exporting `buildDataFlowGraph(perFileIR, callGraph, opts)` — same two positional arguments as `runDeepAnalysis`, same opts-carried budgets/scanRoot/fileContents, same best-effort contract (a failure records a limitation and returns a graph, never throws into the scan). This keeps `graph-builder.js` itself a pure function of already-collected inputs and puts orchestration in one place, exactly as `dataflow/index.js` does for the taint engine.

- **Seeding: match at the call site, mint the data element, seed the entry state — a separate module from `graph-builder.js`.** Recommended `source-seeding.js` (name for E1 to confirm): walk each function's CFG expressions, call `matchSource(expr, file)`, take `accessPathOf(expr)` as the state key, `reclassifySource(entry)` for the category/coverage, `classifyDataElementName(name)` for the data classes, and `dataElementId(canonicalName, discriminatorParts)` for the id — with the discriminator carrying **at minimum the file and the access path**, per §10.4's *"`email` in two unrelated services or schemas must remain two data elements"*. Then call `analyzeFunctionFieldIdentity(fn, seededState, ctx)` per function with a `recordHop` recorder. This is deliberately NOT a change to `driver.js`'s signature: `runFieldIdentityAnalysis` already accepts `opts.recordHop` and `opts.cache`, and the cleanest shape is probably an additional `opts.seedEntryState(fn)` hook rather than a fork of the loop — but note `driver.js`'s own disclosed overwrite hazard (its `cache.set(fn.qid, emptyState(), …)` line, whose comment says the two computations *"are NOT guaranteed to agree … it becomes load-bearing the moment entry states carry real identities"*). **E1 must decide whether seeding goes through `driver.js` or alongside it, and that comment is the reason it is a decision rather than a detail.**

- **Projection: a `DataFlowGraph v1` node is a REGISTRY MATCH, not a provenance node.** The strong recommendation is that E does **not** map `pnode → node`. Instead: a graph node is minted per *(registry decision, call-site location)* — a matched source, a matched sink, a truncation-terminal, an unresolved destination — and the provenance DAG is used only to decide **which source connects to which sink** and **what the hops in between were**. Concretely: enumerate registry-backed sinks; for each, `reconstructPaths(store, thatNodeId)`; each returned `Path` whose terminal is a seeded source location becomes one `flow`, its `dataElementId` becomes `flow.dataElementIds`, and its hop sequence collapses into graph edges. This keeps node counts in the flagship fixture's order of magnitude, keeps `flow.edgeIds` referencing real `edge:` ids, and makes FR-305's *"deduplication may collapse identical internal segments but cannot hide materially different transformations or controls"* implementable — `Path.shape` and `gradePath()` already give the exact signals to decide when two paths are materially different. The `context` dimension (`hashState(entryState)`, up to 16 per function) collapses here too: two contexts of the same function that produce the same source→sink projection are one flow with `alternatePathCount` reflecting the difference, not two nodes.

- **`flow.protectionSummary` is `'not_assessed'` and `flow.policyVerdict` is `'not_evaluated'` on every flow E emits** — both are valid enum members (`FLOW_SUMMARY_VALUES`, `POLICY_STATES`), both are honest, and §10.7's *"must be derived from the individual edge verdicts, never stored as an unsupported independent claim"* is satisfied trivially when every edge verdict is `not_assessed`. **`flow.limitations[]` is where E's real honesty budget goes** — a widened path, a truncated reconstruction, a degraded context, an ambiguous multi-candidate sink match each belong there as text, sourced from `gradePath()`'s `factors[]` rather than re-derived.

- **Transformations: call `recognizeTransformation` at the call site, and fill §10.6's call-site half from the hop record.** D4 supplies `kind`/`reversibility`/`algorithm`/`confidence`/`evidence`; the hop record supplies `location` (`scope`, `nodeId`, `line`) and the access paths (`fromPath`/`toPath`). Two §10.6 fields have no honest source in Milestone 1 and E1 should say so explicitly rather than invent them: *"applies on all feasible paths"* (that is FR-307's all-path proof, which needs path-feasibility reasoning nothing in `src/lineage/` does) and *"control credit granted or denied"* (Decision 2's explicit boundary). Recommendation: emit `appliesToAllPaths: null` and **omit any control-credit field entirely** rather than emit `false`, since `false` reads as "credit was considered and denied" — a claim E has no basis for. `NEVER_EMITTED_KINDS` also forces a choice E1 must make once: when a transformation entity must exist but `recognizeTransformation` returned `null`, is its `kind` `'custom'` or `'unknown'`? (Recommendation: `'unknown'` — `'custom'` asserts "this is a real transform we simply don't have a name for", which is a stronger claim than the evidence supports.)

- **§16.7 Finding 2: prefer the `diagnostics()`-union mechanism over the new node shape.** Of the two options §16.7 offers, unioning the store's degraded targets into the enumerator's candidate set is the smaller, more testable change and does not require adding a sixth `path-store.js` node kind (which would touch `provenanceNodeId`'s discriminator and move every `pnode:`/`pedge:`/`ppath:` id in the tree). Concretely: `path-store.js` already builds `outIndex`, so "a `path` node with zero out-edges whose in-edges carry a `context-cap-degraded` annotation" is computable from the shipped read API without touching that module at all — **`edgesFrom(id).length === 0` plus a `lossReasons`/`annotations` check on `edgesTo(id)`**, which is exactly the shape `gradeHop`'s `DEGRADED_LOSS_REASONS` already recognizes. E1 should confirm this is genuinely computable from the public API (it appears to be; `orphanedPeerSources` is a related-but-different diagnostic and must not be mistaken for it) and, if so, keep the fix entirely inside E's own enumerator. Either way, the resulting graph node's fields are already fixed by §1.1 item 3 and must not be re-derived.

- **Coverage: `graph.coverage` is the ledger, `nodes[]` is the inventory, and BOTH are needed.** AC-11's *"visible with a coverage reason"* is best served by a disconnected source/sink still being a real `nodes[]` entry (with its registry `coverageStatus` and `reason`) that simply participates in no `flow` — that is what makes it selectable in an inventory view — while `graph.coverage` carries the run-level accounting (files/functions analyzed, source and sink match counts by category and coverage status, unmatched categories, budget truncations, parse failures). The flagship fixture's own `coverage` shape (`{languages, parseFailures, destinationResolutionStatus, pathBudgetTruncation}`) is the starting point, not the finished contract. **The one rule to design against explicitly: a node E dropped and a node with no path must be distinguishable in the output, and neither may look like the other.** D3's `unsupported`→`process` preservation rule is the same rule one layer down, and D5's corrected exit criterion (*"every REACHABLE category has a real-code proof, and every UNREACHABLE category has a recorded, tested reason — never silent absence"*) is the model for E's own.

- **Multi-candidate sink matches: represent, do not pick.** Given `res.send(x)` really does return two candidates in different categories, the recommended default is to resolve by the receiver actually present at the call site where that disambiguates (the promotion path D3 explicitly left open), and where it does not, to emit ONE node carrying the plurality category at `coverageStatus: 'partial'` with a `reason` naming the alternatives — mirroring `thirdPartySdk`'s own already-reviewed resolution exactly rather than inventing a second convention.

**Recommended sequencing:** strictly sequential, E1 → E2 → E3 → E4 → E5. Unlike D (whose D2/D3/D4 touched disjoint catalogs and were characterized as parallelizable), **every E increment consumes the previous one's output**: E3 cannot be tested without E2's real store, and E4's ledger counts what E3 emitted. The one genuine parallelization opportunity is that Sub-project **F** (the JS/TS benchmark corpus) can start as soon as E2 lands, since a corpus fixture needs to know what a seeded run detects, not what the graph looks like.

**What to plan first:** E1, and specifically its projection half (§3's second and third bullets). The seeding gap is well-understood and mechanical; the provenance-DAG-to-graph projection is the piece with no precedent in the tree, the piece whose mistake would be inherited by E3/E4/F/G/H, and the piece where "wire the modules together and see what comes out" produces a graph that validates and means nothing.

## 5. Explicitly out of scope for Sub-project E

Confirmed against the parent scoping doc's own §7 global exclusion list and against the §5 table's own F/G/H rows, not re-derived here.

**Inherited from Milestone 1's global exclusions (parent §7):** any language beyond JS/TS; FR-202 external destination *resolution* (E marks a destination unresolved via FR-203; E does not resolve hostnames, providers, routes or cloud resource ids); FR-204/205 DB/queue/object-store field-level mapping beyond category recognition; **any protection-verdict analysis** — transit/at-rest/handling stay `not_assessed`/`unknown` on every edge E emits (Decision 2), and recognizing a transform kind never awards handling credit; policy/governance verdicts (`flow.policyVerdict` is `'not_evaluated'`, `graph.policies` stays empty); any UI or local server/API (Milestone 3, which already has its static-fixture-driven prototype); all seven decision-intelligence capabilities, exports, MCP tools, DPIA/RoPA, simulation, runtime twin and remediation (Milestones 4/5).

**Reserved for later Milestone-1 sub-projects — E must not creep into these:**

- **Sub-project F (JS/TS benchmark corpus, Large).** §22.2's 100+/100+ scale corpus in its own `bench/lineage/` directory, baseline-gated like `bench/cve-replay/`. E proves its behaviour on hand-picked real projects and fixtures; **E does not build the corpus**, and E must not quietly become the corpus by accumulating fixtures. *(Note for whoever plans F: the parent doc's §4 Decision 3 calls the corpus "Sub-project E" while its own §5 table calls it F. The §5 table is the one every subsequent scoping doc — including this one — has followed; the Decision 3 sentence is a stale label from an earlier draft, and F is the corpus.)*
- **Sub-project G (comparison report + light performance harness, Small).** The one-time diff of the engine's real output on the flagship demo repo against the hand-built `flagship-graph.json` (parent §4's explicit scoping of §26's *"comparison against current privacy artifacts"* bullet as a one-time report, **not** a standing harness or a dual-running migration mode), plus the non-blocking performance measurement harness for §21's 35% p50 overhead target. E must produce output G can compare and time; **E must not write the comparison, and must not add a performance gate.** E2's budget measurements (§4's E2 row) are input to G, not a substitute for it.
- **Sub-project H (exit-gate closure, Small).** Running AC-01/AC-02/AC-07/AC-11 and schema completeness against F's corpus. E delivers the AC-11 *mechanism*; **H proves AC-11 *passes on the corpus*.** E should not claim the exit gate.

**Also explicitly not E's:**

- **Modifying `path-store.js`, `path-query.js`, `flow-grade.js`, `engine.js`, `summaries.js` or `field-identity.js`.** E is a consumer, exactly as C4/C5/C6 were consumers of what came before them. The one plausible exception is an additive `opts.seedEntryState` hook on `driver.js` — E1's call, and if taken it must preserve `driver.js`'s existing byte-identical-without-the-option property, the same way `opts.recordHop` already does.
- **Modifying `catalog.js` / `catalog-expanded.js` / `privacy-catalog.js` / `schema.js` / `validate.js` / `dataflow-graph.schema.json`.** D's own "Not in scope" list already forbids the first four for the same reason; the last two are Milestone 0's frozen contract, and a graph that needs the validator relaxed is a graph that is wrong.
- **New detection of any kind.** In particular the AI-destination gap D5 measured and disclosed — all nine `ai-*` sink categories have zero matching catalog entries, so FR-205/AC-07 *"is confirmed not satisfiable by reclassification at all — it needs new detection this sub-project never attempted."* That is inherited unchanged: **E cannot close AC-07 either**, and the Milestone 1 exit gate naming AC-07 is a known, currently-open problem for whoever plans H. Flagging it here so it is not discovered at gate time.
- **Touching `frontend/`.** The prototype consumes `flagship-graph.json` through a build-time-generated, parity-tested copy; a real scan-produced graph is a different artifact with `scope.source: 'scan'`, and rendering it is Milestone 3's.
