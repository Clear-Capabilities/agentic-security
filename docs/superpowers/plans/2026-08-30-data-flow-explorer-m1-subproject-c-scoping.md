# Data Flow Explorer — Milestone 1, Sub-project C Scoping: Path DAG + Bounded Reconstruction

**Status:** scoping document, not an implementation plan. Sub-projects A (field-identity engine core) and B (interprocedural summaries, all six increments B1-B6) are DONE and merged to `main`. This document scopes Sub-project C, the next item in the parent Milestone 1 breakdown (`docs/superpowers/plans/2026-08-30-data-flow-explorer-m1-lineage-engine-scoping.md`, §5, row C: *"Path DAG + bounded reconstruction... `path-store.js`: compact predecessor/provenance structure, path budget/truncation semantics designed alongside it... Multiple-path support (FR-305) and implicit/widened-flow marking (FR-306) land here."*).

## 1. The PRD requirements this sub-project must satisfy

Quoted verbatim from `AGENTIC_SECURITY_DATA_FLOW_EXPLORER_PRD.md` (repo root, untracked per this repo's convention):

- **FR-303 (Path reconstruction):** *"The engine must retain a compact predecessor/provenance DAG from which ordered paths can be reconstructed. It must not eagerly materialize every possible path during scanning because that creates path explosion."*
- **FR-305 (Multiple paths):** *"When several paths connect the same source and sink, the UI must show a path count and allow the user to inspect each path. Deduplication may collapse identical internal segments but cannot hide materially different transformations or controls."*
- **FR-306 (Implicit and widened flows):** *"Implicit/control-dependent and unknown-field widened flows must be visually distinct and lower-confidence. They may not be displayed as the same evidence grade as an explicit field assignment."*
- **§18.4 (Path-explosion controls), the binding constraints on the data structure itself, not just the UI:**
  - Store a provenance DAG, not a list of every expanded path.
  - Cap alternate paths per source/sink pair with an explicit truncation count.
  - Prioritize paths that differ in boundary, transformation, or protection state.
  - Bound interprocedural contexts per function and disclose fallback behavior (already satisfied by B1/B6's context cap + env var).
  - Collapse repeated library/framework nodes into typed summary hops.
  - Run layout and heavy query work in cancellable workers (out of scope for the engine itself — a later-milestone UI concern).
  - **Never translate "path budget exhausted" into "no path."** This is the single most load-bearing constraint: a truncated reconstruction must be distinguishable, in the data itself, from "we looked and there genuinely is no path" — AC-10 requires a persistent partial-coverage banner driven by exactly this distinction.

## 2. The gap: this is a genuinely new capability, not an extension

A dedicated research pass (before this document was written) confirmed, by direct code reading:

- `scanner/src/lineage/field-identity.js`'s state (`Map<accessPath, Set<dataElementId>>`) retains **zero** provenance. `addIdentity`/`joinStates` never record which prior construct — source, transform, prior variable, function parameter — produced a given `dataElementId` at a given path. A join across branches unions sets, discarding which branch contributed which member.
- `engine.js`'s `widenings` array (`{atPath, dataElementIds, reason, line}`) is a flat, append-only diagnostic ledger, not a walkable graph — it records THAT a widening happened, never a hop-ordered predecessor chain.
- Sub-project B's interprocedural summaries (`returnFlat`, `mutatedParams`) are similarly flat sets with no retained call-chain/hop history; `returnByPath` — the one field that could carry structure — is B1's own disclosed, still-unpopulated limitation.
- `DESIGN_INTRAPROCEDURAL.md`'s very first sentence states the scope boundary explicitly: *"Single-function analysis only. No interprocedural resolution, no path DAG..."* — Path DAG was named and deliberately deferred from the design's inception, not an oversight.
- The Milestone-0 flagship fixture (`build-flagship-fixture.mjs`) hand-builds one `flow` object per materialized path (`flowMaskedLog`, `flowRawLog`), each independently repeating its own full `edgeIds` array with no structural sharing — this is a literal illustration of the "list of every expanded path" anti-pattern §18.4 explicitly forbids the ENGINE from producing internally. It is a fine illustrative fixture for a hand-authored example, but not a template for how Sub-project C should compute or store paths.

**Conclusion:** Sub-project C is the first place any predecessor/provenance structure enters this engine at all. It is not a small extension of A/B's existing state — it is new capability built *on top of* A/B's outputs, and the central design risk is doing this WITHOUT requiring an invasive rewrite of A/B's already-hardened, six-round-adversarially-reviewed core state representation (`field-identity.js`'s `Map<path, Set<id>>` shape and its FR-301 invariant). A design that bakes provenance directly into that Map's value type (e.g. `Map<path, Map<id, Set<ProvenanceEdge>>>`) would re-open FR-301's entire correctness surface for re-review under a new, more complex shape — high risk, given how many rounds it took to close the first time.

## 3. Recommended design direction (for the design-spike increment to resolve, not pre-decided here)

Not a final decision — this is what the design-spike increment (C1, below) should evaluate and settle, analogous to Sub-project A's own "Decision 1" reuse-boundary ADR:

- **Reuse the existing, hardened "three hop types" framework** (production / selection / write-out — `DESIGN_INTRAPROCEDURAL.md`'s own exhaustively-reviewed invariant, restated in `scanner/src/lineage/CLAUDE.md`) as the natural emission points for provenance edges, rather than inventing a new taxonomy. Every place `resolveExprIdentities` currently forwards or produces structure is already a candidate provenance-edge site.
- **Record provenance as a parallel, additive output — not a change to `field-identity.js`'s core state shape.** A candidate shape: `analyzeFunctionFieldIdentity` (and its interprocedural counterpart) gain an OPTIONAL accumulator parameter (mirroring how `ctx` was threaded through in B2, itself additive and backward-compatible) that, when supplied, receives `{fromPath, fromId, toPath, toId, kind, nodeId, line, qid}`-shaped hop records as they're discovered — with zero behavior change when the accumulator is absent, preserving every existing test in A/B untouched.
- **`path-store.js`'s own structure** should be the compact DAG itself (nodes = provenance-hop endpoints, deduplicated; edges = hop records), built by CONSUMING the accumulated hop records from a whole-project run (naturally sitting downstream of B4's `runFieldIdentityAnalysis`), with reconstruction (walking the DAG from a sink backward to candidate sources) as a separate, bounded query function over that structure — not computed eagerly during the forward analysis pass.

  > **Superseded in part, 2026-08-30, by increment C4's design task — see `scanner/src/lineage/DESIGN_PATH_PROVENANCE.md` §14.** The bullet above was written before any hop-recording code existed, and three of its claims did not survive contact with the real stream. Recorded here rather than silently ignored:
  >
  > - *"edges = hop records"* — **no.** C1's Decision 2 made records HALF-edges, so an edge is a *pair* (one in-half × one out-half at a shared four-part join key), not a record. §14.3.
  > - *"nodes = provenance-hop endpoints"* is right in spirit but under-specified. A node is `(scope, context, kind, path | siteNodeId, dataElementId)`: `context` is load-bearing (without it §9.4's phantom returns at the node level and `peerContext` becomes decorative), and terminal endpoints (`return`/`escape`/`loss`/`origin`) need their own `kind` namespace rather than a fabricated path token. §14.2.
  > - *"built by CONSUMING… naturally sitting downstream of B4's `runFieldIdentityAnalysis`"* — **deliberately not.** `path-store.js` is a PURE consumer of a hop iterable and must never import `engine.js`/`summaries.js`/`driver.js`. Sitting downstream of the driver would make it untestable today, since a driver run emits zero hops until a source registry exists (Sub-projects D/E). §14.1.
  >
  > Also settled by §14 and worth carrying back here: a single `pathId` (§4's C4 row, below) became **two** functions, `provenanceNodeId`/`provenanceEdgeId`, with `pathId` deliberately left unclaimed for C5's own reconstructed-path entity; and §4's closing "collapsing repeated library/framework nodes… plausibly folds into whichever of D or C4" is resolved as **D, not C4** — C4 has no registry with which to tell a framework function from an application one, and guessing would be the same bug class as a fabricated endpoint.
- **Truncation must be a first-class, explicit value in the data, never an implicit empty result.** Mirror the `unreachable:true`/`not_assessed` precedent already established elsewhere in this codebase (SAST findings, protection verdicts) — a reconstruction result should distinguish `{paths: [...], truncated: false}` from `{paths: [...over budget...], truncated: true, budgetExhausted: true, totalPathsFound: N}`, satisfying §18.4's "never translate budget exhausted into no path" and AC-10's banner requirement directly from the data shape, not bolted on by a caller.

  > **Superseded in part, 2026-08-30, by increment C5's design task — see `scanner/src/lineage/DESIGN_PATH_PROVENANCE.md` §15.** The sketched result shape `{paths: [...], truncated: true, budgetExhausted: true, totalPathsFound: N}` was written before any DAG existed, and two of its four fields did not survive contact with a real reconstruction. Recorded here rather than silently ignored:
  >
  > - *`budgetExhausted`* — **dropped as a separate boolean.** There are FIVE distinct limits that can stop a reconstruction (`expansion-budget`, `candidate-cap`, `depth-limit`, `per-terminal-cap`, `path-cap`), and one boolean cannot say which. Replaced by `truncated: boolean` plus a sorted `truncationReasons: string[]` drawn from that closed vocabulary. §15.4.
  > - *`totalPathsFound`* — **renamed and split, because the original name is a lie under truncation.** A truncated walk does not know how many paths exist; it knows how many it *enumerated*. Replaced by `enumeratedPathCount` / `returnedPathCount` / `droppedPathCount` (the last is §18.4's own "explicit truncation count") plus a per-terminal `terminals[]` breakdown, which is what FR-305's "the UI must show a path count" actually needs. §15.4/§15.5.
  > - *`{paths: [...], truncated: false}` as the whole "not truncated" story* — **insufficient.** It cannot distinguish "genuinely no path" from "you named a node that isn't in this store" from "nothing flows in AND the recording is known-incomplete here" (§14.4's `orphanedPeerSources`). A `noPathReason` field, computed ONLY when `truncated === false`, and an `unknownStartNode` flag close both gaps; §15.4's table pins all five answers as pairwise-distinguishable JSON.
  >
  > Also settled by §15 and worth carrying back here: §4's C5 row says "the backward-walk query function (sink → candidate sources)" — there is still no sink registry (Sub-project D), so the entry point's parameter is `startNodeId`, not `sinkNodeId`, and `sinkCandidates(store)` is an explicitly-labelled structural stand-in (`return`/`escape`/`loss` node kinds) rather than a registry; and §18.4's "cap alternate paths per source/sink pair" is implemented today as a cap per **(terminal node, start node)** pair, which is a genuine per-pair cap rather than a placeholder — a purely global cap was MEASURED to report a real source as having zero paths (§15.5).
- **FR-306's implicit/widened-flow marking** is largely already available as raw material: `widenings`' existing `reason` field (`unresolved-call`, `dynamic-property-key`, etc.) is exactly the signal FR-306 needs surfaced distinctly — Sub-project C's job is to thread this into the DAG's own edge/hop representation (an edge built from a widening event is marked accordingly), not to invent new detection.

  > **Superseded in part, 2026-08-31, by increment C6's design task — see `scanner/src/lineage/DESIGN_PATH_PROVENANCE.md` §16.** The bullet above (and §4's C6 row, below) describe "threading the reason taxonomy into the DAG's own edge representation" — written before any reconstructed-path shape existed. What actually shipped is different in kind, not just in detail: FR-306 is implemented as `scanner/src/lineage/flow-grade.js`, a **standalone, zero-import pure function library** (`gradeHop`/`gradePath`) that reads a `path-query.js` `Path`/`Hop` object and computes a grade — it does NOT write anything onto the DAG's own edge representation, and it deliberately does not (`path-query.js` never gains a `grade` field, per §16.8 item 7c, to avoid moving `C5/4b`'s pinned literal-JSON result shape and to keep `path-query.js`'s own zero-second-import boundary intact). A consumer calls `gradePath(path)` on demand, the same way a consumer calls `reconstructPaths` on demand — nothing is pre-computed or stored.
  >
  > Also settled by §16 and worth carrying back here: C6's design task found and fixed a genuine, previously-unnoticed bug in **already-merged C5 code** — `path-query.js`'s `Path.widenedHopCount`/`lossHopCount`/`shape` undercounted a real widening whenever it lived only in `edge.annotations[]` (an already-hardened C4 design rule, §2.2) rather than the edge's own top-level `widenReasons`/`lossReasons` — fixed in `materialize()`, confined to four lines, independently verified four separate times across this sub-project's own review process to change no other assertion in the tree. This is the sub-project's own precedent that a later increment's design phase can — and, when it finds one, should — remediate a real defect in an earlier, already-closed increment's shipped code, scoped as a small separately-committable fix rather than a re-open of the closed increment.
  >
  > **Sub-project C is complete as of C6 (`c63c6338`).** One item remains genuinely open and is binding on whoever scopes Sub-project D next (not Sub-project C's own job to close): a §13.6 context-cap-degraded binding edge's target is unreachable from `sinkCandidates()` today (its node has zero out-edges and is neither a `return`/`escape`/`loss` kind), so a normal sink-rooted reconstruction never surfaces it — §18.4's own "truncation must never look like no-flow" constraint re-opening at the query boundary. A candidate "truncation-terminal" node shape is sketched in §16.7 Finding 2.

## 4. Sub-project breakdown (recommended)

| # | Increment | Depends on | Size | What it delivers |
|---|---|---|---|---|
| C1 | **Design spike: provenance recording approach** | B (done) | Medium | Resolves §3's open design question as a short ADR-style note (mirroring Sub-project A's own Decision 1 precedent): the hop-record shape, the accumulator-parameter mechanism and its exact injection points across the three hop types, and confirmation (via a small proof-of-concept against real parsed code, not just a paper design) that this can be added without changing `field-identity.js`'s core state shape or regressing any of A/B's existing ~211 tests. |
| C2 | **Intraprocedural hop recording** | C1 | Large | Wires the accumulator into `resolveExprIdentities`/`analyzeFunctionFieldIdentity` for all three hop types, single-function scope only (mirrors Sub-project A's own intraprocedural-first sequencing). Every existing intraprocedural test scenario from Sub-project A (object literals, aliasing, ternaries, computed keys, spread/rest, wildcards) needs a corresponding hop-recording proof, not just an identity-correctness proof — this is likely the largest single increment, proportional to how much surface Sub-project A itself had to cover. |

Interacts directly with B5's recursion refinement (a hop recorded during a bottom-stub round must not be presented as if it were the refined round's real hop) and B6's context cap (a context-capped-and-degraded call's hop must be marked accordingly, not silently merged with a precisely-resolved one). |

| C5 | **Bounded path reconstruction + truncation semantics** | C4 | Large | The backward-walk query function (sink → candidate sources), the alternate-path cap with explicit truncation count, the "prioritize paths that differ in boundary/transformation/protection state" ordering rule, and the truncation-is-never-silent data shape from §3. | C6 | **FR-306 wiring: implicit/widened-flow marking on the DAG** | C4 | Small | **DONE.** Shipped as `scanner/src/lineage/flow-grade.js` — a standalone, zero-import grading library (`gradeHop`/`gradePath`) computed on demand from a reconstructed `Path`/`Hop`, not threaded into the DAG's own edge representation (see the carry-back box above, `DESIGN_PATH_PROVENANCE.md` §16). **Explicitly out of scope for Sub-project C:** any `DataFlowGraph v1` graph OUTPUT (producing real `node`/`edge`/`flow` entities from the DAG) — that is Sub-project E's job, which depends on this sub-project's output plus Sub-project D's source/sink registries; any UI/layout/worker concerns from §18.4 (cancellable workers, visual distinctness) — Milestone 3; transformation-*kind* recognition beyond what `widenings`' existing reasons already provide — Sub-project D; collapsing repeated library/framework nodes into typed summary hops (§18.4's own bullet) — plausibly folds into whichever of D or C4 turns out to be the more natural home once C4's actual DAG node shape is settled; not pre-decided here.

**Recommended first target:** C1, for the identical reason Sub-project A's own design spike was recommended first — this is the highest-uncertainty, most load-bearing piece (get the hop-record shape or injection points wrong here and every later increment inherits it), and a focused design pass with a small real-code proof-of-concept, before committing to a full task-by-task implementation plan for C2 onward, is what de-risked A's own six-round saga from being worse than it was.
