# Data Flow Explorer Milestone 2 — Destinations and Protection Proof: Scoping Document

**Status:** scoping only — no implementation plan yet, and **no production code was touched to produce this document**. Structure, tone, and rigor follow `docs/superpowers/plans/2026-08-30-data-flow-explorer-m1-lineage-engine-scoping.md` (Milestone 1's own scoping doc), which is the template this document was written against.

**Source:** `AGENTIC_SECURITY_DATA_FLOW_EXPLORER_PRD.md` §26 (Milestone 2 deliverables + exit gate, lines 1798–1809), §14 "Protection and policy requirements" (FR-401–405, lines 1108–1186), AC-03 through AC-09 and AC-12 (lines 1607–1657), §22 "Accuracy and release gates" (lines 1514–1558), §29–§30 (success metrics / risk table, lines 1984–2049). Cross-checked against the real current state of `scanner/src/lineage/` (Milestone 1, complete and merged as of 2026-08-31), `scanner/src/dataflow/`, `scanner/src/sast/`, and `scanner/src/posture/`.

## 1. What Milestone 2 actually is (restated precisely)

**Deliverables (PRD §26, near-verbatim):** external resolver; database/table/column and queue/topic mapping; AI-BOM linkage; transit, at-rest, and handling analyzers; cross-boundary normalization; policy and governance integration.

**Exit gate (PRD §26, verbatim):** "AC-03 through AC-09 and AC-12 pass; false-protected release gate passes."

**What Milestone 1 already ruled out of its own scope, and handed forward unstarted** (per that scoping doc's own out-of-scope table and its "What is NOT here yet" section): external destination resolution (FR-202, `not-attempted` even at the `sink-registry.js` FR-203 "unresolved destination" level — see §2 below for what partial signal DOES exist), DB/queue field-level mapping beyond category recognition, all of §14's protection-verdict *analysis* (`protection.js` defines the verdict *model* only; every edge Milestone 1 emits legitimately carries `not_assessed`/`none` on all three dimensions), and policy/governance verdicts. Milestone 2 is where all four become real.

**What Milestone 2 explicitly is NOT**, confirmed against the PRD's own milestone table (§26): the local API/server and any UI (Milestone 3's job — Milestone 0 already shipped a static-fixture-driven prototype these views run against); every decision-intelligence extension (Executive Risk Story, What-If Simulator, Time Machine/drift, Regulatory Overlay, Runtime Digital Twin, Third-Party/Cross-Border Intelligence, Blast-Radius/Remediation — Milestones 4/5); any language beyond JS/TS (Milestone 1's own JS/TS-only reading of §22.1 carries forward unchanged — nothing in §26's Milestone 2 deliverable text mentions language expansion).

## 2. What already exists to build on (so tasks don't re-derive it)

The single biggest finding of this scoping pass: **Milestone 2 is not starting from zero.** Several existing modules — built for the pre-lineage finding/taint pipeline, years before this PRD — are direct, load-bearing precedent for FR-401 through FR-405. None of them is graph-aware yet; all of them encode real, already-proven detection or policy logic that Milestone 2 should reclassify/adapt rather than reimplement, following the exact reuse discipline Milestone 1's own Decision 1 established ("reuse the pure detection/matching logic; never the old engine's mutable state").

**Transit protection (FR-401) — call-site detection already exists, but is not edge-aware.**
`scanner/src/sast/crypto-protocol.js` is a mature, six-family regex detector (`detectTlsMinVersion`, `detectTlsNoVerify`, `detectWeakCiphers`, `detectEcbMode`, `detectStaticIv`, `detectWeakHash`, plus KDF/JWT rules) already covering every signal FR-401 asks for: cleartext/scheme detection is implicit in its cipher-suite and URL-adjacent patterns, TLS minimum version (`detectTlsMinVersion`, line 86), certificate/hostname verification disabled (`detectTlsNoVerify`, line 117 — `rejectUnauthorized: false`, `NODE_TLS_REJECT_UNAUTHORIZED=0`, Python `verify=False`/`CERT_NONE`, Go `InsecureSkipVerify: true`, Java/`.NET` trust-all patterns), and weak-cipher usage (`detectWeakCiphers`, line 160). **Its emission granularity is exactly what FR-401 needs — a specific file:line — but it is a standalone, data-flow-blind pattern match**: it has no notion of which sensitive field, if any, is carried by the network call it just flagged, and no connection to a `DataFlowGraph v1` edge id. It answers "is this call site's TLS configuration bad" independent of "does PCI data cross it."

**At-rest protection (FR-402) — the real gap. Confirmed, not assumed: zero existing detectors.**
`grep -rn "CWE-311\|CWE-312" scanner/src/sast/*.js` returns nothing. No SAST module in this codebase emits either CWE for missing/weak at-rest encryption today. `scanner/src/sast/iac-cloud-templates.js` has exactly one at-rest-adjacent rule and it is transit, not storage: a Bicep "storage account permits unencrypted HTTP traffic" check (line 168, `CWE-319`/`iac-transit-encryption`) — its one comment mentioning "encryption at rest" (line 118) is documentation prose on an unrelated public-endpoint finding, not a check. `scanner/src/sast/iac-terraform.js` has no encryption-keyword hits at all. This means FR-402 has **no reusable call-site or config-parsing precedent anywhere in this codebase** — it is Milestone 2's largest genuinely-new-detection sub-project, and the PRD's own FR-402 text ("the presence of any cipher in the same file or repository cannot establish at-rest protection for a store") is itself an implicit acknowledgment that a naive reuse of `crypto-protocol.js`'s file-proximity style would be the wrong shape here even where it exists.

**Handling taxonomy (FR-403) — transformation-*kind* recognition already exists (Milestone 1, D4), but stops one hop short of a verdict.**
`scanner/src/lineage/transform-catalog.js` (Milestone 1 Sub-project D, increment 4) already classifies a call site into exactly the vocabulary FR-403 needs — `mask`/`hash`/`tokenize`/`encrypt`/`redact`/`encode`/`decode`/`truncate`/`aggregate`/`normalize`/`decrypt`, each with a reversibility tag — via `recognizeTransformation(calleeDescriptor)`. This is real, tested (42 entries, `test/lineage/transform-catalog.test.js`), and was built specifically anticipating this handoff: its own module header states it deliberately does **not** decide "control credit granted or denied" (§10.6/Decision 2 of the Milestone 1 scoping doc), reserving that for Milestone 2's FR-401–405 analyzers by name. `scanner/src/dataflow/privacy-taint.js`'s `classifySink`/`SINK_PATTERNS` (lines 44–74) is a **different, coarser** mechanism worth naming precisely so it isn't confused with the above: it classifies a sink's *category* (`log`/`response`/`outboundHttp`/`thirdPartySdk`/`fileWrite`/`s3Upload`/`emailSend`, seven labels) and — confirmed by reading `annotatePrivacyTaint` (lines 82–172) — has **no raw/masked/hashed/redacted distinction at all**: every PII-classified variable reaching any of those seven sink categories produces a finding unconditionally, with zero awareness of whether a `transform-catalog.js`-recognizable call sits between source and sink. FR-403's real remaining gap is exactly the connective tissue between the two: walking a `path-store.js`/`path-query.js` reconstructed path (Milestone 1 Sub-project C, already shipped) and asking, per hop, whether `transform-catalog.js` recognizes it — nothing does this today.

**AI-BOM linkage (FR-205's remainder) — already substantially closed by Milestone 1, not a fresh build.**
`scanner/src/posture/aibom.js`'s `PROVIDER_PATTERNS` (lines 30–49) extracts provider + model name for OpenAI/Anthropic/Vercel-AI/Google/Mistral/Cohere/Groq/Bedrock/Replicate calls — already proven, corpus-backed extraction. Milestone 1's own Sub-project H closed AC-07 by bridging this into `dataflow/catalog.js` (4 new sink entries) and `lineage/sink-registry.js`'s `CWE_MAP` (1 new row), with a real over-firing precision bug found and fixed via `receiverBase` constraints (`test/catalog-ai-model-provider-precision.test.js`). What is genuinely still missing, confirmed by the Milestone 1 scoping doc's own closing table: AC-07's "provider, model when known, **network protection**" clause and AC-01's per-sink "handling/transit/at-rest verdict" clause were both explicitly left `not_assessed`/absent, pending Milestone 2. In other words, **AI-BOM linkage's own remaining M2 work is almost entirely downstream of FR-401 (transit analyzer) and FR-202 (external resolver) applied to AI sink nodes Milestone 1 already put in the graph** — not a new detection surface of its own.

**External resolver (FR-202) — a coarse category-level precedent exists; the literal destination facts do not.**
`scanner/src/lineage/sink-registry.js`'s `CATEGORY_EXTERNALITY` table (Milestone 1, D3) already tags every sink category `internal`/`external`/`unknown`, and `source-registry.js`'s `SOURCE_CATEGORY_EXTERNALITY` (D2) does the source-side equivalent. `sink-registry.js`'s `reclassifySink(entry, {destinationUnresolved, blockingExpression})` (D3) and `coverage.js`'s `detectUnresolvedDestination`/`resolveSiteDecision` (Sub-project E, increment 4) already close **FR-203** — a real, shipped, tested mechanism for "the sink is known but its destination expression could not be statically resolved," including the receiver-vs-argument eligibility split that a measured false-positive bug forced (`cursor.execute(sql)` must not fire on its argument; `fetch(url)` must). **This is real signal, but it answers a much coarser question than FR-202 asks.** `externality` is a three-value enum per sink *category* ("is this kind of destination generally internal/external/unknown"), never a specific hostname, cloud account, SDK identity, or trust zone for a specific call site. FR-202's nine required facts (literal URL/scheme, method, hostname/port, route, SDK/provider, model/service name, env/config chain, cloud resource id, trust zone) and its eight-value `resolutionStatus` enum (`literal`/`resolved_from_constant`/`resolved_from_config`/`resolved_from_schema`/`declared_service`/`runtime_corroborated`/`dynamic`/`unknown`) have no existing implementation anywhere in this codebase. The gap between "category-level externality" and "resolved destination identity" is real and should not be underestimated by anyone reading `externality: 'external'` as a head start on FR-202 — it answers a different, coarser question.

**Database/table/column and queue/topic mapping (FR-204, and the queue/topic half of FR-201) — the matching MECHANISM already exists, in the old engine's shape.**
`scanner/src/posture/cross-lang-orm.js` already builds a `table.column → tainted-source` registry from ORM call sites (Mongoose/Sequelize/Prisma/SQLAlchemy/Django ORM/ActiveRecord/GORM/Eloquent — file header, lines 1–15) and emits cross-file chain findings when a later read of the same table.column is reached. `scanner/src/posture/cross-lang-queues.js` does the topic-name-pairing equivalent for Kafka/SQS/RabbitMQ/Redis-streams/Pub-Sub producer/consumer pairs, already handling the "topic name is a constant-folded expression, not a literal" case (`topic: 'inferred'`). **Both are real, working, corpus-proven mechanisms for exactly what FR-204/FR-201's queue bullet ask for — but both are built on the OLD boolean/chain-finding taint engine, not the lineage graph.** This is the identical shape of gap Milestone 1's own Decision 1 named for `dataflow/summaries.js`'s `SummaryCache`: the *mechanism* (table.column keying, topic pairing, schema parsing) is reusable; the *state* it's built on is not.

**Cross-boundary normalization (FR-304) — the same pattern, for schema-derived edges.**
`scanner/src/posture/cross-lang-openapi.js`, `cross-lang-grpc.js`, and `cross-lang-graphql.js` already parse OpenAPI/gRPC/GraphQL contract artifacts and correlate them with code-level call sites, each already conservative-by-construction (only chains when both ends are unambiguously mapped; ambiguous match → zero findings, never a guess — `cross-lang-openapi.js` header, lines 9–15). This is real precedent for FR-304's "identify whether an edge is code-derived, schema-derived, manually declared, or runtime-corroborated" requirement, again in the old chain-finding shape rather than the lineage graph's edge shape.

**Policy verdicts (FR-404) — a near-complete precedent already exists at the PII-field granularity.**
`scanner/src/dataflow/privacy-sink-policy.js` is, functionally, an existing (data class × sink) policy-permission engine: `.agentic-security/privacy-policy.json` declares `allow` rules keyed on `sink` + optional `class`/`environment`/`destination` (regex-matched against the real sink expression text, e.g. `stripe.track`, not just its category), fail-closed on an unset context (an environment-scoped rule never matches an unknown environment — `_matchesEnvironment`, line 75), and — critically for AC-09 — every permitted flow is recorded on a visible `policyExemptions` array rather than silently dropped (`annotatePrivacyTaint`, lines 145–152), carrying exactly the fields AC-09 asks for: the matching rule, reason, environment, and destination (`permittingRules`, line 123). This is a binary permitted/not-permitted model, not FR-404's five-state enum, and it has no `approver`/`owner`/`expiration` fields — but the *mechanism* (fail-closed rule matching keyed on data class + sink + environment + destination, with mandatory visible exemption disclosure) is exactly the shape AC-09 exercises.

**Governance unknowns (FR-405) — already built, and the PRD's own text says so.**
`scanner/src/dataflow/privacy-governance.js` implements the exact "existing `manual_required` discipline" FR-405's text names by name: `GOVERNANCE_FIELDS` (line 33) is `purpose`/`lawfulBasis`/`subject`/`retention`/`residency`/`recipient`/`transfer`/`minimization`/`consent`/`access`/`deletion` — an eleven-for-eleven match against FR-405's own field list — with every field defaulting to a `MANUAL_REQUIRED` sentinel unless operator-supplied via `.agentic-security/privacy-governance.json`, and the operator-vs-manual provenance always distinguishable downstream (`governanceRecordFor`, line 74). This module already exists, is already wired into the DPIA artifact, and needs no new detection logic — only, if Milestone 2 chooses to touch it at all, a re-keying from "per data class" to "per data element/flow" to match the lineage graph's finer granularity.

**The protection verdict model itself (Milestone 0) — confirmed still a pure model, not an analyzer.**
Read directly: `scanner/src/lineage/protection.js`'s `emptyProtection()` (line 18) returns `{verdict: 'not_assessed', evidenceGrade: 'none'}` for all three dimensions (`transit`/`atRest`/`handling`), exactly as Milestone 1's own scoping doc (Decision 2) said it would leave things. `aggregateVerdicts()` (line 43) already implements the PRD §8.4 risk-precedence reduction (`unprotected > mixed > unknown > protected > not_applicable > not_assessed`) needed for AC-12's "one branch encrypts, one doesn't → mixed or unprotected" requirement — this exists and needs no new code, only real per-dimension verdicts to aggregate.

## 3. Real gaps — nothing today does these

1. **At-rest protection detection of any kind (FR-402).** Confirmed zero existing CWE-311/312 detectors. The single largest, most novel piece of new detection work in the whole milestone.
2. **A transit/handling analyzer that is EDGE-aware, not just call-site-aware.** `crypto-protocol.js` and `transform-catalog.js` both answer "what does this specific call site do" — neither knows which lineage edge, if any, the call site corresponds to, nor which data element crosses it. Nothing today joins a `path-store.js` hop's `siteNodeId`/call-site information to a SAST-style pattern match at that exact site.
3. **Literal external-destination extraction (FR-202's nine facts, its eight-value `resolutionStatus`).** `sink-registry.js`'s category-level `externality` and `coverage.js`'s FR-203 unresolved-destination detection are real but answer a coarser question (§2 above). Extracting an actual hostname/scheme/SDK-provider/cloud-resource-id from a call site's literal or config-chain arguments is unbuilt.
4. **Transformation *control-credit* computation (FR-307, and by extension FR-403's real verdict, not just its taxonomy label).** `transform-catalog.js` recognizes a call; nothing walks a reconstructed path (`path-query.js`'s `reconstructPaths`) and checks "does a recognized transform apply on this hop, on EVERY feasible path to this sink" — the exact AC-12 requirement ("a transform on one branch cannot make the full flow green").
5. **DB/table/column and queue/topic facts projected into `DataFlowGraph v1` node/edge shape.** `cross-lang-orm.js`/`cross-lang-queues.js` produce chain *findings*, not graph nodes carrying `provider`/`host`/`database`/`schema`/`table`/`operation`/`column` (FR-204) or topic/stream identity as first-class node fields.
6. **A policy verdict enum beyond binary permitted/not.** `privacy-sink-policy.js` has no `conditionally_permitted` or `manual_review_required` state, and no `approver`/`owner`/`expiration` fields — real gaps against FR-404's full five-state text, though (see Decision 3 below) not all of them are actually required by any Milestone-2 exit-gate AC.
7. **A precisely defined "false-protected release gate."** See §4 below — this is a genuine scoping finding in its own right, not merely an implementation gap.

## 4. Decisions this scoping makes explicitly

**Decision 1 — FR-401/402/403 are built as lineage graph-walk extensions consuming reused call-site PRIMITIVES, never as new SAST detectors in their own right, and never as a rewrite of the lineage engine's own core state.**
The PRD's own AC-12 ("a transform on one branch cannot make the full flow green") and FR-307 ("a transform receives control credit only when the analyzer can associate it with the selected field on the selected path and determine that it applies on all relevant feasible paths") cannot be answered by a file/line pattern match alone — they require per-path reasoning that only `path-store.js`/`path-query.js`/`flow-grade.js` (Milestone 1 Sub-project C, already shipped) already provide. **Recommendation:** each of FR-401/402/403 is implemented as a new analyzer module under `scanner/src/lineage/` that (a) reuses `crypto-protocol.js`'s and `transform-catalog.js`'s existing PATTERN-RECOGNITION functions as pure, call-site-keyed evidence lookups — never their finding objects, never a new independent SAST rule — and (b) walks `reconstructPaths()`'s output, joining a path's hops to the underlying call sites via the existing `siteNodeId`/CFG-node linkage already threaded through the provenance DAG, to compute a per-edge, per-dimension `protection.js`-shaped verdict. This mirrors Milestone 1's Decision 1 exactly: reuse the pure detection logic, reimplement the state/wiring that connects it to the graph. FR-402 (at-rest) is the one dimension with no existing call-site primitive to reuse at all (§3.1) — its analyzer is closer to a from-scratch build, correlating IaC config evidence (where present) with store nodes, and should be sized and staffed accordingly (see Sub-project C below).

**Decision 2 — the "false-protected release gate" is NOT precisely defined anywhere in the PRD, confirmed by direct search, and this document defines it.**
`grep -n "false-protected"` across the whole PRD returns exactly three hits: the Milestone 2 exit-gate line itself (1809, names it but does not define it), §29's "Accuracy and false-protected gates pass for each declared language" (2004, same — names, does not define), and §30's risk-table mitigation cell "Path-specific proof, fail to unknown, false-green benchmark gate" (2080, a design principle, not a gate specification). The only NUMERIC anchor anywhere in the document is §22.3's release threshold: "false `protected` verdict rate below 1%." That bullet is one line among nine other release thresholds in the same list, with no stated denominator, no per-dimension-vs-aggregate scoping, no stated corpus mechanism, and no methodology — it is a target number, not an operationalized gate, and treating it as one without saying so would be exactly the kind of silently-invented answer this scoping document is instructed not to produce. **This scoping document defines the gate as follows, to be validated (and, if needed, revised) before Sub-project H below is planned in detail:**
- **Scope:** evaluated **per protection dimension** (`transit`, `atRest`, `handling` — each independently, never aggregated into one rate), matching §14.1's own independent-fields model and AC-12's requirement that one dimension's verdict never launders another's.
- **Denominator:** every labeled-corpus edge for which the engine's own analyzer asserts `verdict: 'protected'` on that dimension (a precision-style rate over the engine's own positive claims — matching §22.3's literal phrase "false `protected` verdict RATE," which is a rate of false positives *among protected claims*, not a rate over the whole corpus).
- **Numerator:** any such edge where the labeled ground truth is actually unprotected, OR where the emitted `evidenceGrade` overstates what the analyzer actually observed (e.g. a `declared`-only signal rendered with `code_and_config`-strength evidence — a distinct failure mode §14.1 exists specifically to prevent, and one a naive true/false accuracy count would miss entirely).
- **Mechanism:** modeled on `bench/mutation/`'s verdict-flip pattern (referenced in the root `CLAUDE.md`), not a static labeled-corpus percentage alone — for every fixture the engine marks `protected` on a dimension, a companion semantics-changing mutation (TLS-verification-disabled variant; missing-at-rest-config variant; raw-vs-masked-log variant) must flip that specific dimension's verdict away from `protected`. A mutation that fails to flip is scored as a false-protected defect directly, the same anti-overfitting shape `bench/mutation/` already uses elsewhere in this codebase, rather than trusting a labeled-corpus percentage that a narrow, corpus-shaped analyzer could game.
- **Home:** a new `bench/protection-verdict/` directory (or an extension of `bench/data-lineage/`, to be decided at Sub-project H's own planning time — not decided here), gated into the release check the same way `bench/mutation:check` is, never folded into the pre-push gate's existing `bench:cve-replay`/`bench:layer-recall` checks, which score detection presence, not verdict correctness.

**Decision 3 — FR-404 is scoped narrowly to what AC-09 actually requires; FR-405 is deferred to Milestone 4 in full.**
Re-reading AC-03 through AC-09 and AC-12 (the exit-gate ACs) specifically for a policy or governance requirement: **AC-09 is the only one that names a policy verdict** ("a policy allows masked PII to a named analytics provider in production… the flow remains on the diagram with a permitted badge, matching rule, reason, environment, destination, and evidence"). No exit-gate AC mentions `prohibited`/`conditionally_permitted`/`manual_review_required`, an approver/owner, an expiration, or any of FR-405's eleven governance fields at all. **Recommendation:** Milestone 2 implements only the slice of FR-404 that AC-09 exercises — adapting `privacy-sink-policy.js`'s existing mechanism (§2 above) into the lineage flow shape, populating `flow.policyVerdict` (already a Milestone-0-defined schema field, per `lineage/CLAUDE.md`'s own `validate.js` description) with `permitted` when a matching rule fires and `not_evaluated` when no policy is configured (matching `privacy-sink-policy.js`'s existing empty-policy default), carrying rule/reason/environment/destination straight through. The `prohibited` state is already implicit (no permitting rule matches — today's unconditional-finding default), so no new code is needed for it either. The two states with no existing precedent at all — `conditionally_permitted` and `manual_review_required` — and the approver/owner/expiration fields, are explicitly deferred: nothing in the exit gate requires them, and Milestone 4 already lists "Regulatory Obligation Overlay" as a deliverable, which is a more natural home for a fuller policy-state and governance-workflow build than bolting it onto Milestone 2 because §14 happens to mention it. FR-405 in full is deferred to Milestone 4 outright — `privacy-governance.js` already satisfies its letter today at the PII-field granularity, no exit-gate AC exercises it at the flow granularity, and re-keying it is real but non-urgent work that does not block AC-03 through AC-09/AC-12.

**Decision 4 — the DB/queue/cross-boundary sub-projects reuse the MATCHING mechanism of `cross-lang-orm.js`/`cross-lang-queues.js`/`cross-lang-openapi.js`/`cross-lang-grpc.js`/`cross-lang-graphql.js`, never their chain-finding state, following Milestone 1's own Decision 1 precedent exactly.**
Each of these modules is real, corpus-proven, and answers close to the right question (table.column registries, topic-name pairing, schema-endpoint correlation) — but each is built to emit a `cross_language: true` chain finding against the old taint engine, not a `DataFlowGraph v1` node/edge. Reusing their state directly would repeat the exact mistake Milestone 1's Decision 1 warned against for `dataflow/summaries.js`. **Recommendation:** the pure schema-parsing/matching logic (OpenAPI/gRPC/GraphQL endpoint maps, ORM table.column keying, queue topic-name pairing) is extracted or called directly; the lineage-side sub-projects build their own graph-shaped state on top, per §18.1's binding reuse rule ("may reuse pure IR, call-graph, access-path, string-domain, and schema-parsing utilities. May not share mutable taint state with the general engine").

**Decision 5 — AI-BOM linkage (FR-205's remainder) is not staffed as its own detection sub-project; it rides on Sub-projects A (external resolver) and B (transit analyzer).**
Per §2's finding above, the only pieces of AC-07/AC-01's AI-related clauses still open after Milestone 1 are "network protection" (transit) and "provider, model when known" as a *resolved destination* fact (external resolution) — both already-scoped Milestone 2 work applied to AI sink nodes that already exist in the graph. A dedicated "AI-BOM linkage" sub-project would mostly duplicate A/B's own work against a different node subtype. **Recommendation:** fold AI-BOM linkage into Sub-projects A and B's own acceptance criteria (an AI-provider external node resolves its provider/model exactly as any other external node does; an AI API call gets a transit verdict exactly as any other network edge does) rather than budgeting it separately.

| B | **Transit protection analyzer (FR-401)** | A (dynamic-scheme cases need destination-resolution status), Milestone 1 `path-query.js`/`flow-grade.js` | **Large** | New `lineage/`-side analyzer joining a reconstructed path's hops to their underlying call sites and consulting `crypto-protocol.js`'s existing TLS/cipher pattern-recognition functions (reused as pure evidence lookups, per Decision 1) to compute a per-edge `protection.transit` verdict + evidence grade.
