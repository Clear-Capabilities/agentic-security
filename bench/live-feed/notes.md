## How this run came about, and what changed in the code because of it

The run was done in five passes over the same 56 entries. Passes 1 to 4 were development passes: each exposed a defect (below), the defect was fixed with a
failing test first, and the corpus was re-run. **Every table above is from the fifth, final pass**, run at the commit named at the top with no code change
after it except this report and its generator. Numbers quoted below as "first pass" are from the earlier passes and were measured with the code as it then stood;
they are evidence for the defect, not a statement about the current code.

### Defects found by the run, and fixed (each has a test in `scanner/test/haskell/haskell-live-feed-scan.test.js` that fails without the fix)

| # | Defect | Evidence from the run | Fix |
|---|--------|-----------------------|-----|
| 1 | `scanHealth.languageCoverage.optionalModes['hackage-live']` was hard-coded `selected:false`, so a scan that had just queried OSV reported the live feed as "not selected". | First scan of `examples/haskell-app/vulnerable` with the feed on showed 6 OSV requests (one batch, five records) and `not_selected`. In the first pass 11 projects reported `not_selected` after querying the feed. | `liveFeedOptionalState` maps what the refresh actually did (`ok`, `partial`, `failed`, or "selected but did not run"). |
| 2 | The scan result's finding dropped `matchStatus`, `matchReason`, `declaredRange`, `resolution`, so a `possibly-affected` finding (only a range is known) read exactly like an `affected` one, and `advisory` was empty. | In the first pass 12 of 54 projects with Hackage findings carried no `matchStatus` in the scan JSON. | The report layer carries the fields through. |
| 3 | `--no-network` and `AGENTIC_SECURITY_OFFLINE=1` still sent registry-metadata requests (npm, PyPI, crates.io, Maven Central): the OSV lookups honoured offline mode, `queryRegistries` did not. | Second pass: **16 of 56 projects, 7576 requests across the two offline modes**, hosts `registry.npmjs.org`, `pypi.org`, `crates.io`, `search.maven.org`; e.g. hledger-web's vendored jquery caused a real `GET registry.npmjs.org/jquery` (status 200) under both flags. Final pass: 0 requests of any kind in both offline modes on all 56. | `queryRegistries` returns immediately when offline. This is not specific to Haskell. |
| 4 | A dependency declared with no version bound (`build-depends: aeson`) was carried as "no range" and reported `unknown` ("neither a resolved version nor a declared range is known"). In Cabal it means any version. | First pass: **159 of 684** advisory-by-component rows (23%) were `unknown` for this reason alone. | An unbounded declaration is an any-version range: `possibly-affected` (or `affected` when every version is). A component with truly nothing known stays `unknown`. |
| 5 | A freeze file was applied to every manifest in the repository. ShellCheck's only freeze file is `builders/linux.armv6hf/cabal.project.freeze`, for one release builder; it became the "resolved" aeson 2.2.3.0 of the root package, so `affected` was claimed where only a declared range (`possibly-affected`) is known. | Found by adjudicating the first sample (sample row: ShellCheck v0.11.0, aeson, `affected`, judged incorrect). | A freeze or lock file resolves the manifests at or below its own directory; the nearest enclosing one wins. |
| 6 | A package the project itself defines was reported as a dependency: aeson's own test suite has `build-depends: aeson`, cabal-install's tree depends on `cabal-install`. Advisories about the project's own (fixed) version were raised against it. | Found by adjudicating the second sample (aeson-2.3.2.0 `possibly-affected` against HSEC-2026-0007 which that very version fixes; cabal-install `possibly-affected` against HSEC-2025-0005 which 3.4.0.0 fixed). Judged incorrect. | Dependencies on a package defined by a `.cabal` or `package.yaml` in the scanned tree are not Hackage dependencies. |
| 7 | An unbounded use in a test suite, next to a library that pins the same package to a fixed range, raised `possibly-affected` for a version the solver can never pick. | 7 of 273 (project, package, advisory) groups. Examples: hadolint `aeson` (library `>=2.2.3 && <2.3`, test suite unbounded), tls `crypton`, postgresql-simple `aeson`. | An unbounded use inherits the unconditional bounds the same manifest declares for that package elsewhere. Conditional bounds and bounds in another manifest are not inherited. |

Deliberate-breakage check, run for all seven: with each fix removed, its test fails (7 of 7), and with the fix in place it passes. `npm run test:haskell` 150/150 and
`npm run test:language` 218/218 after the last code change; `npm run bench:language-support:check` exits 0.

### Found and NOT fixed (evidence only)

Update, after this run: five of the bullets below were fixed in a later change (each is marked **Fixed after this run**, and the sentence after the marker says how). Their figures are the evidence as measured on the code of this run; they are not re-measured here, and no table above was regenerated after the fix.

* **Fixed after this run: the evaluator now reports the worst status per package, scope and advisory, with the components that carry it in `carriedBy` and the milder uses in `otherUses`.** Distinct declared ranges were collapsed by name and scope. `hackageComponents` keeps the first use of a package per scope, so a second manifest's different range is never evaluated. Measured on the final trees: in 3 of 224 (project, package, advisory) groups a declared range with a worse status was hidden by the kept one (dhall-haskell 1.38.0 `cryptonite` kept `possibly-affected`, another use `affected`; fourmolu `aeson`; hlint `base`). Fixing it multiplies findings per package, which is a product decision.
* **Fixed after this run: unconditional `constraints:` of a project file that governs the manifest are intersected with the declared range (an exact pin inside it becomes the resolved version), and `allow-newer` / `allow-older` widen it, both disclosed in the finding.** Project-level `constraints:` and `allow-newer` were not applied to declared ranges. liquidhaskell's `cabal.project` has `aeson >= 2.2.3.0` while its packages declare `aeson` with no bound; the status is judged on "any version". Here the verdict happens to be unchanged (`possibly-affected`), but a constraint such as `aeson >= 2.2.5.1` would turn it into `not-affected`.
* **Fixed after this run: compiler-provided packages are one finding per advisory (`grouped: 'compiler'`) that lists every member, is counted apart from dependency findings, and is decided against the project's pinned compiler or reported as "unknown compiler"; every use keeps its `ghc-component:*` status row.** GHC-component advisories dominated the match counts. 313 of the 479 `affected` or `possibly-affected` rows (166 + 313) are `ghc-component:*` rows (`base` HSEC-2023-0007 is unfixed from base 3.0.3.1, so every project is `ghc-component:affected` or `possibly-affected`). They are correct per the record and are reported as compiler-provided, but they are noise next to an actionable dependency finding.
* **Scan time in deep mode is not feed-related but limits any project-scale measurement.** pandoc 3.12.1 (both the Hackage tarball and the GitHub tag) and cabal-install 3.18.2.0 did not finish a default (deep) scan inside a 10 minute budget. One probe each: `agentic-security scan <pandoc tree> --no-network --no-deep` finished in 7.6 s (exit 3); the same flags on cabal-install did not finish in 300 s, so for cabal-install deep mode is not the whole story. An earlier cabal-install cold scan, run on a heavily loaded machine in the first pass, reported `durationMs` 1,459,919. These three entries ran on reduced trees (see the per-project table).
* **Fixed after this run: the prefetch now runs as soon as the manifests are read, before the expensive passes.** The feed lookup happened near the END of a scan (cabal-install first pass: 1447.7 s into a 1459.9 s scan). A scan that is killed or fails before that point has no advisory data even though the feed is enabled; that is correct behaviour, but it means a timeout looks like "feed unavailable".
* **Fixed after this run: the narrative builds its own label ("Advisory HSEC-... in foo 1.3") when a finding has no `vuln`, and omits the location clause when there is no file; the finding itself is unchanged.** Blast-radius text for Hackage findings read "undefined on `app.cabal:12`". The Hackage supply-chain entry has no `vuln` field for the narrative builder. It was not changed because the same field feeds finding identity.
* **A project with Haskell sources and no Hackage manifest** (purescript v0.14.0 has only `stack.yaml`) gets `hackage-live: not_run` and "no Hackage advisory snapshot is loaded" because nothing was looked up. Honest, but noisy.

### What the real feed did NOT exercise

On the date of this run the final pass fetched 12 distinct advisory records (16 in the earlier passes, before packages a project defines itself were excluded). **Every failure path of the feed was therefore untouched by real traffic:** no record fetch failed, no batch response carried a next-page token, no package was left uncovered, no timeout or rate-limit response occurred, and no project had more than the 500-package cap (largest: 276). Those paths are covered only by the stand-in server in `scanner/test/haskell/haskell-advisory-feed.test.js`; "0 uncovered" here says the feed is complete on this corpus, not that its failure handling works against the live service.

## Limits of this measurement

* **Sample size and labels.** 34 adjudicated rows. The labels are the harness-running model's, not a human's, and that model also wrote parts of the code it judged: shared blind spots are possible. The verdict is about the status given the advisory record's machine-readable ranges and the manifest / freeze / plan evidence. It says nothing about whether the vulnerable function is reachable or a platform condition holds (HSEC-2024-0003 is Windows-only; the matcher does not model that and the labels do not either).
* **A 26/26 sample is not "100% precise".** The lower bound of the 95% interval is 0.868. Two earlier samples (not published) drawn on the pre-fix code contained 3 incorrect rows (ShellCheck, defect 5; cabal-install and aeson, defect 6); they were fixed before this sample was drawn, so this sample measures the post-fix matcher. Its seed is the default in `sample.mjs`, fixed before the draw and not tuned.
* **Projects were chosen by availability**, not at random: 40 declared-range entries (17 Hackage tarballs, the rest tagged application releases), 4 with a freeze file, 4 with a stack lock, 8 with a cabal plan generated at the pinned index state under GHC 9.14.1. Several tags are recent and therefore less likely to depend on vulnerable versions; older tags were included on purpose for the `affected` cases. Of 13 plan attempts, 5 did not solve under this GHC (scotty, persistent, servant-server, tls, dhall; attempted without tests enabled) and were dropped from the corpus.
* **Resolved versions from a plan are the solver's choice in this environment**, not necessarily what the project's maintainers build with.
* **The feed's state** is the state of `api.osv.dev` on the date above. Advisory records change; rerunning on another day changes the status counts.
* **Timings** come from a shared machine (see the load figures) with up to 5 scans in parallel; wall times are upper bounds, CPU times are steadier. The three reduced-tree entries have no real scan time. The first-pass timings (taken at a 1-minute load of about 150 from unrelated processes) are not reported anywhere in this file.
* **Requests are counted inside the scanner process** (`fetch`, `http`, `https`). A request made by a child process or a raw socket would not be seen.
* **Statuses come from `eval-statuses.mjs`**, which re-runs the scanner's own supply-chain pass over the scan's file set and the snapshot the scan wrote; the scan JSON itself carries only findings. For all non-reduced projects the number of packages the scan sent to OSV equals the number of unique packages the evaluation saw.
